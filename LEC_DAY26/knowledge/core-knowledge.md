## 1. Core Concepts

- **MCP spec 2026-07-28 (Streamable HTTP, stateless)** — The current MCP protocol revision. Removes session state from the protocol entirely (not just "optimizes" it). Why it matters: turns every MCP call into a plain HTTP request that load balancers, WAFs, and service meshes can route/parse without shared session storage. (Explicit, §2, slide 5–6)
- **Statelessness as wire format, not architecture advice** — Older guidance said "design stateless" as an architectural recommendation; the 2026-07-28 spec makes it a protocol requirement (no `Mcp-Session-Id`, no `initialize`/`initialized` handshake, no SSE resume via `Last-Event-ID`). Related: every request now carries its own `_meta` (protocolVersion, clientCapabilities, clientInfo, prefixed `io.modelcontextprotocol/`). (Explicit, slide 5–6)
- **`server/discover` RPC** — A method servers must implement; used for health checks (returns version + capabilities + identity), replacing a plain `200 OK` check. (Explicit, slide 8)
- **Server-issued handle (for state)** — When a server needs cross-call state, it issues a handle, passed back explicitly as a tool parameter — the replacement mechanism for what session used to provide. (Explicit, slide 5, 33)
- **MRTR (Multi Round-Trip Requests)** — Replaces the old "server calls back the client" mechanisms (`roots/list`, `sampling/createMessage`, `elicitation/create`). Every result must now carry `resultType`: `"complete"` or `"input_required"`. Old servers lacking this field are treated by the client as `"complete"`. Infrastructural meaning: a pending human-approval wait is no longer a hanging open socket — it's a named state. Trade-off: stream resume capability was also removed, so a broken stream = lost in-flight request; client must retry with a new ID ⇒ tools must be idempotent or use an idempotency key. (Explicit, slide 7)
- **`Mcp-Method` / `Mcp-Name` headers** — `Mcp-Method` is mandatory on every POST of Streamable HTTP; `Mcp-Name` is mandatory for `tools/call`, `resources/read`, `prompts/get`. `x-mcp-header` lets tool parameters push custom headers upstream. Lets gateways/rate-limiters/WAFs route and meter by header instead of parsing JSON body. (Explicit, slide 9, quoted from release notes)
- **`cacheScope` + `ttlMs`** — Spec-required fields on list/read endpoint responses (e.g. `tools/list`). `cacheScope: "public"` allows shared intermediary caching; `"private"` restricts to client only. `ttlMs` signals freshness. (Explicit, slide 11)
- **Deterministic tool ordering for prompt-cache hit rate** — Spec recommendation: servers should return tools in a stable/deterministic order because prompt cache is prefix-matching, and the tool catalog sits at the start of that prefix; an unordered dict source will silently break cache hits and cost full price per request. (Explicit, slide 11; connects to Day 22's prompt-cache economics)
- **Well-Known URI discovery** — `https://{domain}/.well-known/agent-card.json` (RFC 8615 pattern). Note: A2A v0.3 renamed this from `agent.json` to `agent-card.json`; old clients requesting the old path get a 404 and silently conclude "no agent here." (Explicit, slide 12)
- **MCP Registry (official)** — Provides: `server.json` format (name, location npm/URL, run command, env vars, capabilities), DNS-verified reverse-namespace naming (`io.github.user/server`), REST API + OpenAPI spec. Does NOT provide: private servers ("not supported" per docs), security scanning (delegated to package registries/aggregators), stability guarantees (still preview, "may reset data"). (Explicit, slide 13)
- **Internal/private fleet registry** — Recommended pattern for internal fleets: run your own registry to the official OpenAPI spec, behind a moderation gate that does: description scanning at registration, definition pinning + drift alerts, namespace verification, version pinning. Rationale: the official registry authenticates *who owns a name*, not that the code is safe. (Explicit, slide 13)
- **Deprecation policy (official)** — Active (use freely) → Deprecated (still fully functional, don't build new on it) → minimum 12 months → Removed. 2026-07-28 deprecated: Roots (→ tool parameter), Sampling (→ direct API call), Logging (→ stderr or OpenTelemetry, see §12), HTTP+SSE (→ Streamable HTTP), DCR RFC 7591 (→ Client ID Metadata Documents). (Explicit, slide 14)
- **A2A Task lifecycle (8 states)** — `SUBMITTED → WORKING → {COMPLETED | FAILED | CANCELED | REJECTED | INPUT_REQUIRED | AUTH_REQUIRED}`. Old deck taught 6 states, missing `REJECTED` and `AUTH_REQUIRED`. `AUTH_REQUIRED`: agent neither refuses nor fails — it pauses and requests permission (who grants it, for how long, logged where = content of §7). (Explicit, slide 16)
- **Agent Card** — JSON document serving two roles at once: discovery document AND security contract. Contains `name`, `version`, `skills` (with `id`, `tags`), `capabilities.extendedAgentCard`, `securitySchemes` (5 types: APIKey, HTTPAuth, OAuth2, OpenIdConnect, MutualTls). When `extendedAgentCard` is true, an authenticated client gets a more detailed card ⇒ capability disclosure itself becomes an authorization decision. A2A v1.0 (Google → Linux Foundation, 6/2025), 150+ organizations, 3 bindings: JSON-RPC, gRPC, HTTP+JSON/REST — binding choice is an infra decision. (Explicit, slide 17)
- **Protocol-aware proxy / data plane** — A proxy that reads `Mcp-Method`/`Mcp-Name` at the header level (vs. generic L7 proxies that only see `POST /mcp`, TLS, source IP). Enables: route/meter/block per tool, cache `tools/list` responses by `ttlMs` + `cacheScope`, federate multiple MCP servers behind one endpoint, check identity+policy per call. This capability is only cheap in 2026 because of §2 (no session to trust) and §3 (method name on header). (Explicit, slide 18)
- **agentgateway** — Open-source Rust data plane; security/observability/governance for agent→LLM, agent→tool, agent→agent; runs on bare metal, VM, container, K8s. (Explicit, slide 19)
- **kgateway** — Envoy-based K8s gateway (CNCF); v2.1 is the first release integrating agentgateway as the AI data plane instead of extending Envoy further. (Explicit, slide 19)
- **Envoy AI Gateway** — Being deprecated, along with Envoy Inference Extension; functionality re-implemented in agentgateway. (Explicit, slide 19)
- **Routing techniques (5, ranked by cost)** — Keyword/rule matching (≈0 cost, ≤5 destinations); Semantic/similarity (1 embedding, 5–50 destinations); Learned cost-quality model (train+infer, large pools/real cost pressure); Cascade/uncertainty (ask cheap model first, escalate on low confidence; 1–2 calls; quality floor + cost ceiling); LLM-as-router (1 full call; complex/context-dependent routing). (Explicit, slide 20)
- **Model routing vs. agent routing (distinct problems)** — Model routing asks "which model answers" (quality/cost trade-off); agent routing asks "who handles this" (capability match, reading the `skills` field in the Agent Card directly). Conflating them is described as the source of most bad routers. (Explicit, slide 20)
- **SPIFFE/SPIRE** — Answers "which process is running, and where does it get its credential?" — cryptographic, attested identity (SVID). (Explicit, slide 21)
- **OAuth (in this context)** — Answers "what is it allowed to do at this resource?" — scope of permission at a resource server. Production agents need BOTH SPIFFE and OAuth (they answer different questions). (Explicit, slide 21)
- **DPoP (Demonstrating Proof of Possession)** — Binds an OAuth token to a key held by the client; a stolen token alone can't be replayed from another process. Flagged as a top roadmap priority because MCP's current OAuth handling "fails silently" — errors are not diagnosable, and VS Code's MCP client can't declare an audience, making scoped tokens infeasible there. (Explicit, slide 15)
- **Tool poisoning / Rug pull / Tool shadowing-squatting** — Three attack families, all rooted in the same structural cause: MCP clients inherit trust from the server they connect to and don't re-verify over time. Tool poisoning = adversarial instructions embedded in tool descriptions/schemas/response content (treated by agent as trusted operational context) — defense: scan descriptions at registration, treat tool text as untrusted input. Rug pull = server changes a tool's description after client approval — defense: pin tool definitions + drift alerts. Tool shadowing/squatting = malicious server overrides or impersonates another server's tool — defense: namespace verification + allowlist from a private registry. (Explicit, slide 22)
- **Three lines of defense (fleet security)** — (1) Registry that's secure-by-design — every server has a record before it runs ("known good" baseline). (2) Pin tool definitions + drift alerts — the tripwire for rug pulls. (3) Every call goes through a gateway that re-checks identity and policy — ON EVERY CALL. Line 3 is only cheap because the protocol is stateless (§2); in the old session model, "re-check every call" was expensive and got cut — which is exactly where incidents happen. (Explicit, slide 23)
- **Context tax at fleet scale** — Paradox: successfully integrating more MCP servers degrades the agent, because most MCP clients by default load ALL connected servers' full tool definitions into context before the agent reads the first request. Example (explicit): GitHub's MCP server alone dumps 43 tool definitions into context. Illustrative figure: ≈77K tokens for tool definitions before any real work begins (with 50+ tools). This is framed as an infrastructure decision (how many servers you connect, how the client loads them), not a prompt-engineering problem. (Explicit, §8, slide 24)
- **Tool Search (lazy tool loading)** — Tool definitions retrieved on demand instead of preloaded. Reported effect: with 50+ tools, ≈77K → ≈8.7K tokens, retaining ≈95% of the context window. (Explicit, slide 25; reported/vendor figure, flagged in source as not a guarantee)
- **Code execution with MCP / "Code Mode" (Cloudflare's term)** — MCP schemas translated to a TypeScript API; the model writes code that calls that API. Intermediate data stays in the execution environment, never transits the model's context. Reported: one workflow ≈150,000 → ≈2,000 tokens; Code Mode case: 2,500 endpoints, 1.17M → ≈1,000 tokens. Side benefit (explicit, notable): credentials also never enter context — Code Mode exposes only two tools (`search()`, `execute()`); generated code runs in an isolate and calls the API via binding, so the API key never passes through the model. (Explicit, slide 25)
- **Programmatic tool calling** — Tools invoked inside a code execution environment so results don't need to transit context; example given: reading/editing thousands of spreadsheet rows without overflowing context. (Explicit, slide 25)
- **`defer_loading: true`** — Per-tool flag marking a tool for on-demand retrieval instead of preload; requires a dedicated tool-search server (regex or BM25 variant) to be declared. Trap: the tool-search tool itself must NOT be marked `defer_loading`, and at least one non-deferred tool must remain, or the API returns 400 ("All tools have defer_loading set"). Common failure mode: auto-generated configs that flag every tool as deferred. (Explicit, slide 26)
- **Progressive discovery (roadmap item)** — Upcoming spec feature (8/2026 roadmap): server opens up its catalog gradually instead of dumping it all; lazy-loading techniques from slide 26 are becoming default protocol behavior. Budget/checkpoint/limits (§9–11) remain the developer's responsibility regardless. (Explicit, slide 26)
- **Two independent axes: Harness vs. Deployment** — Four build patterns for agents: self-written loop (you provide harness AND deployment), Tool Runner/SDK (SDK provides harness, you deploy), Claude Agent SDK (SDK provides full harness + built-in tools, you deploy), Managed Agents (provider provides both harness and deployment, container per session). Three of four options hand you a harness and leave deployment to you — exactly today's subject matter. (Explicit, slide 27)
- **Agent loop as a workload shape** — Contrasted against classic request/response: lifetime minutes-to-hours (vs. ms-to-s); number of infra calls decided by the model, unknown in advance (vs. known in advance); cost is long-tail distributed (vs. near-constant); termination is not guaranteed — can loop forever (vs. always terminates); scaling signal is unclear/TBD (vs. RPS, CPU). (Explicit, slide 28)
- **Model-visible vs. model-invisible budgets** — `max_tokens`: hard cutoff per response, model doesn't know it exists, just gets cut off. `Task budget`: advisory, token-based, for the whole loop; server inserts a visible countdown the model sees while generating, so it self-paces and wraps up gracefully; minimum 20,000. `Session budget` (Managed Agents): hard dollar cap, enforced by the platform. Key point (explicit): a budget only the model can see changes its behavior; a budget only your dashboard sees changes nothing — parallels alerting (fires after money is spent) vs. enforcement (actually stops the agent). (Explicit, slide 29)
- **Four isolation levels for agent-generated code execution** — V8 isolate (language-runtime isolation, JS only; tool calls via binding not syscall; starts in ms/MBs; narrowest — no arbitrary binaries, no GPU). Container (shares host kernel; <90ms start; weakest of the kernel-based levels). gVisor (user-space kernel intercepting syscalls; GPU via ioctl proxy not PCIe passthrough; fast start; good isolation). Firecracker microVM (hardware virtualization via KVM, separate kernel per sandbox; VFIO passthrough for GPU; <150ms start, <5MB overhead; strongest isolation boundary). Trend is monotonic: stronger boundary = slower start (isolate ≈100x faster than container because it builds no kernel). Choose based on what the generated code is permitted to touch, not on milliseconds. (Explicit, slide 30)
- **Sandbox as part of state** — A complete checkpoint must include all three: conversation history, tool-call history, AND sandbox filesystem. Missing the third: agent resumes "remembering" it wrote a file that no longer exists, and confidently continues on a nonexistent world. (Explicit, slide 30)
- **CPU as the wrong scaling signal** — Illustrative example: one inference pod serving 50 concurrent requests shows CPU 5–8% ("idle") while GPU is at 95%; a CPU-based autoscaler would shrink the cluster right as it's about to overload. For async/queue-shaped workloads, backlog is the real signal, not resource utilization. Cited figure (flagged as illustrative, sourced): a 2026 report across 23,000+ production clusters measured average CPU at 8% with 69% CPU over-provisioning. (Explicit, slide 31)
- **Scale-by-backlog** — Read queue depth from Redis/RabbitMQ/SQS; react within 30–90 seconds; scale-to-zero when queue is empty. Rationale: a new inference pod needs 3–10 minutes (image pull, weight loading, CUDA graph capture); resource-based autoscaling only reacts after overload — you're always one beat behind load. Capacity unit is NOT "request" — plan by concurrent sessions, queue depth, and sandbox inventory. An agent waiting on human approval still holds a sandbox — consuming no CPU/tokens, invisible on dashboards; sandbox inventory runs out before GPU does. Caveat (explicit): backlog-based scaling doesn't fit agents holding in-memory state, and 30–90s is still too slow for real-time — this is why §2 (statelessness) and §11 (durable state) must precede this slide. (Explicit, slide 32)
- **Three-tier state ladder** — (1) Externalized state (any replica serves any request) — e.g. Redis (TTL), PostgreSQL (history). (2) Framework checkpointing (graph state saved per step, resumable) — e.g. LangGraph's PostgresSaver/RedisSaver/DynamoDBSaver. (3) Durable execution (function resumes exactly where it stopped after a crash; long waits cost nothing) — e.g. Temporal, Restate, DBOS (Postgres as source of truth), Inngest, Hatchet. Tier 1 remains valid but is insufficient alone for multi-hour agents with approval checkpoints. Explicit connection: the state the protocol removed doesn't vanish — it becomes an application-layer artifact with an explicit name (server-issued handle), which is exactly what a durable-execution engine needs. Same idea appears at three layers: MCP `input_required`, A2A `INPUT_REQUIRED`, and a waiting workflow. (Explicit, slide 33)
- **Context editing vs. Compaction** — Context editing: DELETES old tool results or thinking blocks — failure mode is transparent (you know it's gone). Compaction: SUMMARIZES old history server-side — failure mode is data that seems retained but isn't ("summarized" still sounds complete). Default compaction trigger threshold: 150K tokens. Both are often conflated as "context management" but are two separate features/parameters/failure modes. (Explicit, slide 34)
- **Silent compaction-block drop bug** — The compaction block lives in `response.content`; the API uses that exact block to replace the compacted history segment in the next request. Common WRONG pattern (extracting only `response.content[0].text` and appending that) silently loses compaction state — no error, conversation simply stops being compacted and grows until it breaks, typically mid-long-run (worst timing). Correct pattern: append the full `response.content` block, not just extracted text. (Explicit, slide 35, with code example)
- **Compaction as a safety-relevant event** — Illustrative timeline: at hour 0, safety rules + working history are both present; by hour 3, after summarization, safety rules from the early preamble can be dropped because the summarizer (optimized for task continuity) treats them as stale/irrelevant boilerplate — with no error logged. Fix is infrastructural, not a prompt fix: pin safety rules outside the region subject to compaction — at the top-level system prompt, or re-injected as a system message mid-conversation — rather than trusting they survive summarization. (Explicit, slide 36)
- **Trace context propagation via `_meta`** — 2026-07-28 spec formally documents OpenTelemetry trace-context propagation through three `_meta` keys: `traceparent`, `tracestate`, `baggage` (W3C Trace Context). Flow: orchestrator generates trace ID → propagated through A2A to each agent → propagated into `_meta` of every MCP call. The gateway (§6) is the natural enforcement point — since you don't control every team's agent code but do control the request path — inject `traceparent` if missing. Vocabulary: `gen_ai.operation.name` models a full agent run as a span tree (`invoke_agent`, `execute_tool`, `plan`…). MCP conventions live in the same repo as GenAI conventions ⇒ shared vocabulary. (Explicit, slide 37)
- **GenAI OpenTelemetry semconv stability status** — As of mid-2026, ALL `gen_ai.*` attributes/spans/metrics/events are labeled "Development" — none are "Stable." 2026-06-12 (semconv v1.42.0): GenAI conventions (incl. MCP) moved to their own repo. Recommendation: still use it (best vendor-neutral option, spec is actively moving toward it), but isolate attribute-name mapping in one code layer, and don't build dashboards assuming attribute names are permanent. (Explicit, slide 38)
- **Cross-agent observability metrics** — Only meaningful once multiple agents exist: rate of falling into `INPUT_REQUIRED`/`AUTH_REQUIRED` (how much work is stuck waiting on a human), mis-routing rate, p95 per hop, cost per agent and per tool. (Explicit, slide 38)

## 2. Relationships & Mechanisms

- **Statelessness (§2) enables header-based routing (§3) enables cheap protocol-aware proxying (§6) enables cheap per-call re-authorization (§7's "line 3 of defense")** — explicit causal chain repeated across slides 6, 9, 18, 23: without sessions, there's nothing stale to trust, so re-checking identity/policy on every call becomes "cheap and natural instead of an expensive thing to cut." (Explicit)
- **MCP call → protocol-aware proxy → routing/metering/caching**: Input = HTTP POST carrying `Mcp-Method`/`Mcp-Name` headers → Process = proxy reads headers (not body) to route, meter per tool, check cacheScope/ttlMs, enforce identity/policy → Output = routed/metered/cached request reaching correct backend replica. Why each step matters: avoids expensive/fragile JSON body parsing that generic L7 proxies require. (Explicit, slide 9, 18)
- **Prompt cache prefix mechanism**: tool catalog and system prompt are the stable prefix; messages are the changing suffix. If a server returns tools in inconsistent order (e.g., from an unordered dict), the entire prefix shifts, cache misses completely, full price is paid per request "without knowing why." Depends-on: deterministic tool-list ordering. (Explicit, slide 11)
- **MRTR mechanism (Input → Process → Output)**: Input = server can't finish yet → Process = server returns `resultType: "input_required"` with `inputRequests` (e.g. elicitation) → client retries the SAME request now carrying `inputResponses` → Output = server resumes/completes. Why it matters: converts a would-be hanging socket into a named, resumable state; trade-off is loss of stream-resume, pushing idempotency responsibility onto tool implementers. (Explicit, slide 7)
- **Lazy tool loading mechanism (Input → Process → Output)**: Input = client connects to server with many tools → Process = a dedicated tool-search server (regex/BM25) is declared; other tools flagged `defer_loading: true`; tool definitions retrieved on demand at call time → Output = drastically reduced upfront context (≈77K→8.7K tokens example). Constraint: at least one tool must remain non-deferred, and the tool-search tool itself cannot be deferred, or the API errors with 400. (Explicit, slide 26)
- **Code Mode mechanism (Input → Process → Output)**: Input = MCP tool schemas → Process = translated into a TypeScript API; model writes code against that API; code executes in an isolate and calls upstream via binding → Output = intermediate data and API keys never enter model context, only two tools (`search()`, `execute()`) are exposed to the model. Depends-on: code execution isolation infrastructure (§10). (Explicit, slide 25)
- **Compaction trust chain**: safety rules injected at session start → compaction event (triggered at 150K tokens default) summarizes old history → summarizer may drop preamble-looking content (including safety rules) as it looks like stale boilerplate → no error is raised → guardrail silently gone. Mitigation depends on: keeping safety rules OUTSIDE the compactable region (top-level system prompt or re-injected mid-conversation). Contrasts with: context editing, which deletes visibly rather than summarizes plausibly. (Explicit, slide 34–36)
- **Trace propagation mechanism (Input → Process → Output)**: Input = orchestrator generates trace ID → Process = trace ID propagated through A2A calls to each agent, then into `_meta.traceparent` of every downstream MCP call; gateway enforces/injects `traceparent` for requests missing it → Output = one trace spanning orchestrator → agent → tool, using shared `gen_ai.*` semantic-convention vocabulary. Depends-on: gateway sitting on the request path (§6), since agent code from other teams isn't directly controllable. (Explicit, slide 37)
- **Scale-by-backlog mechanism (Input → Process → Output)**: Input = queue depth signal from Redis/RabbitMQ/SQS → Process = autoscaler reads backlog (reacts in 30–90s) rather than CPU/GPU utilization → Output = pods scaled proportional to actual work backlog, scale-to-zero when empty. Why not CPU: CPU can read "idle" (5–8%) while GPU is saturated (95%) on the same pod, causing a CPU-based autoscaler to shrink right before overload. Depends-on: durable state / statelessness (§2, §11) since backlog-based scaling doesn't suit agents holding state only in memory. (Explicit, slide 31–32)
- **Isolation-level trade-off (monotonic relationship)**: stronger isolation boundary (V8 isolate → container → gVisor → Firecracker microVM) correlates with slower startup time and higher overhead; explicit reason given — building/virtualizing a kernel costs time isolates don't pay. Selection criterion is what the generated code must be able to touch (e.g., GPU access, arbitrary binaries), not raw startup latency. (Explicit, slide 30)
- **A2A Task states vs. MCP `input_required` vs. durable-execution "waiting"**: all three are described as the same underlying idea expressed at three different layers — a paused-but-not-failed state that needs to be named and stored rather than treated as a hung connection. (Explicit, slide 33)
- **Registry trust model vs. attack surface**: MCP official registry verifies name ownership via DNS namespace, NOT code safety; this gap is explicitly identified as "where vendors install lock-in" and also as the structural opening exploited by tool-poisoning/rug-pull/shadowing attacks — all three attacks share the root cause that MCP clients trust a server at connection time and never re-verify. (Explicit, slide 12, 22)
- **Model routing vs. agent routing — dependency distinction**: Model routing = quality/cost trade-off across LLMs; agent routing = capability matching via Agent Card `skills` field. Conflating the two is cited as the primary cause of poor routing systems — they should be solved as separate problems, with a fallback chain (primary → backup → human) to avoid dead ends. (Explicit, slide 20)
- **SPIFFE + OAuth as complementary, not substitutable**: SPIFFE answers process identity; OAuth answers resource-level permission; production agents need both simultaneously, and an authorization chain where each hop holds its own SVID by role enables full audit ("who did this," something a shared API key can never answer). Critical distinction flagged (explicit): acting "on its own behalf" vs. "on behalf of the end user" are different grants — conflating them is how an agent ends up reading data the requesting user isn't authorized to read. (Explicit, slide 21)

## 3. Examples & Distinctions

- **Day 9 (1 server) vs. Day 26 (40 servers) framing** — Day 9: local stdio or single remote process, tools defined in code, "who calls" is trivially "me," errors read from terminal log, cost = one conversation's cost. Day 26: many replicas/versions coexisting, tools from other teams/companies, every call must answer "who's calling, what are they calling," errors live at hop 4 of a trace, cost must be attributed per-agent/per-tool. (Explicit, slide 3)
- **"Three things the old deck taught wrong"** — (1) Transports: old deck said stdio/HTTP+SSE/WebSocket; reality 8/2026 is only stdio and Streamable HTTP (HTTP+SSE deprecated since 2025-03-26; WebSocket was never a standard transport) — building per old slide means modern clients can't connect. (2) Agent Card path: old `/.well-known/agent.json` vs. new `/.well-known/agent-card.json` (A2A v0.3) — old clients get a silent 404 and conclude "no agent." (3) SDK import: `from mcp.server import Server` (old) vs. SDK v2's `MCPServer`; `stateless_http`/transport options moved from constructor to `run()`. Lesson: 4 spec versions in 2 years (2024-11-05 → 2025-03-26 → 2025-11-25 → 2026-07-28) — check the changelog before building, and log the check date in the README. (Explicit, slide 4)
- **Discovery mechanism comparison** — Well-Known URI (best for domains you control, easiest automation) vs. gated Registry (best for enterprise/marketplace, "centralized governance") vs. direct config/hardcode (best for tightly-coupled systems, dev environments). Key protocol difference: MCP has an official registry with an OpenAPI spec; A2A has no standard registry API — docs call this "a still-evolving area," explicitly flagged as where vendor lock-in gets installed. (Explicit, slide 12)
- **Tool poisoning vs. Rug pull vs. Tool shadowing/squatting** — Similarity: all three exploit the same trust-inheritance gap (client trusts server at connect time, doesn't re-verify). Difference: tool poisoning = malicious content embedded IN a tool description/schema/response at any time; rug pull = a SPECIFIC tool's description changes AFTER approval; shadowing/squatting = a different (malicious) server overrides/impersonates another server's tool identity. Distinguishing criterion: timing and vector of the malicious change (embedded content vs. post-hoc edit vs. impersonation). (Explicit, slide 22)
- **Real 2025–2026 incident examples (explicit, named)**: SmartLoader/Oura Ring MCP (2/2026) — attacker built 5 fake cross-forking GitHub accounts to fabricate trust signals, submitted a cloned package to a real MCP registry; LuaJIT payload dropped StealC malware, persisted via a scheduled task disguised as a Realtek driver; detection signal was that the original author wasn't in the contributor list. Also cited: npm `postmark-mcp` backdoor (9/2025); Invariant Labs tool poisoning (4–5/2025); WhatsApp MCP rug pull (4/2025); MCPoison in Cursor (CVE-2025-54136); three mcp-server-git RCE CVEs (CVE-2025-68143/68144/68145). (Explicit, slide 22)
- **Context editing vs. Compaction** — Similarity: both are informally called "context management." Difference: context editing deletes (transparent loss); compaction summarizes server-side (loss that looks like retention). Distinguishing criterion: whether old content is removed outright vs. rewritten/summarized. (Explicit, slide 34)
- **Request/response vs. Agent loop as workloads** — Lifetime (ms–s vs. minutes–hours), call count (known vs. model-decided/unknown), cost (near-constant vs. long-tail), termination (guaranteed vs. not guaranteed), scaling signal (RPS/CPU vs. "?", answered in §10 as backlog). (Explicit, slide 28)
