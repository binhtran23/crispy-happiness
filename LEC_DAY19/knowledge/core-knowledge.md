## 1. Core Concepts

- **Vector Embedding** — dense numeric vector representing the meaning of text/image/audio; similar meaning ⇒ vectors close in space (e.g., "cloud computing"/"server infrastructure"/"data center" cluster, cos≈0.92). Why it matters: foundation of semantic search (vs. SQL exact match). Related: cosine similarity, embedding models. (Slide 4/56)

- **Embedding Models (2026 landscape)** — explicit comparison table: gemini-embedding-2 (3072d, API, multi-modal), text-embedding-3-large (3072d, $0.13/M, high quality, OpenAI), text-embedding-3-small (1536d, $0.02/M, cheap baseline), cohere embed-v4 (1536d, API, PDF/image, VPC), bge-m3 (1024d, self-host, BAAI, multilingual — best for Vietnamese per VN-MTEB), Qwen3-Embedding (1024d+, self-host, OSS multilingual). Explicit warning: table will be outdated within weeks — "learn how to choose, not memorize." (Slide 6/56)

- **VN-MTEB** — Vietnamese benchmark (arXiv 2507.21500, 07/2025): 41 datasets, 6 tasks, 18 models, used to select embeddings by evidence rather than hype. bge-m3 (multilingual generalist) beats its own Vietnamese fine-tuned variant (Vietnamese_Embedding) on broad benchmark, but fine-tuned models can still win on narrow domains — must measure on your own data. Caveat (explicit): VN-MTEB is translated from English MTEB, so it measures language capability, not Vietnamese culture/domain. (Slide 7/56)

- **Matryoshka Representation Learning (MRL)** — embeddings (e.g., text-embedding-3-large) trained to be truncatable: 3072d → 256d while 256d still beats ada-002 @1536d on MTEB. Saves 6× RAM/disk and vector-DB cost; apply when scaling >10M vectors. (Slide 6/56)

- **Similarity Metrics** — three explicit metrics: Cosine (range [-1,1], angle only, default for text embeddings, unit-norm models make dot=cosine), Dot Product (includes magnitude, faster — no division — used by ColBERT/DPR), Euclidean/L2 (triangle inequality enables IVF/kd-tree, used for CLIP image/wav2vec audio; for unit-norm vectors d²=2(1−cos)). Rule: metric must match the pretraining objective — wrong metric degrades recall 10–20%. (Slide 8/56)

- **Multi-modal Embeddings** — contrastive learning maps text/image/audio encoders into one shared embedding space. Models: CLIP (OpenAI, foundational text+image), SigLIP (Google, backbone of ColPali), jina-clip-v2 (multilingual incl. Vietnamese), ImageBind (Meta, 6 modalities), Gemini Embedding 2 (GA 04/2026: text+image+video+audio+PDF in one 3072d space, 100+ languages, MRL truncatable). Use cases: visual search, content moderation, video indexing, medical (X-ray+report). (Slide 9/56)

- **Vector Database** — a database purpose-built to store and query (approximate) nearest-neighbor vector search. Compared explicitly (VectorDBBench 2025, 1M vectors/768d/HNSW/top-10): Pinecone (managed, REST/gRPC, P99 8–22ms, best for production), Weaviate (self/cloud, GraphQL, multi-modal, ~10ms), Qdrant (self/cloud, REST/gRPC, payload filtering, binary quantization, ~5ms, best for self-hosted), pgvector (Postgres extension, SQL WHERE filtering, 15ms, best when you already have Postgres). (Slide 10/56)

- **FAISS** — Meta (2017) library (not a database, no server), C++/Python; GPU search of 1B vectors top-K <1s; implements IVF, HNSW, PQ, OPQ, IVF-PQ under one API; in-memory + on-disk indices. In 2026 still used as the embedded tier inside Milvus, Vespa, pgvector-rs. Related: Deep Metric Learning (triplet loss/FaceNet, contrastive loss, ArcFace angular margin) is the pre-LLM ancestor of modern contrastive pretraining (CLIP, SigLIP). Pre-LLM use cases: face recognition, Pinterest visual lens, RecSys candidate generation, plagiarism/dedup, audio fingerprinting (Shazam). (Slide 11/56)

- **Three Storage Tiers for Vectors** — In-memory/HNSW (RAM, 5–20ms, highest cost, for hot ≤10M latency-critical); On-disk/DiskANN (local SSD, ~30ms, medium cost, for 100M+ still-interactive); Object storage (S3/GCS, ~100ms, lowest cost, for huge sparse-query corpora). Amazon S3 Vectors (GA 12/2025): first native object-storage vector store, 2B vectors/index, 10,000 indexes/bucket, up to 90% cost reduction; the saving comes from storage price (object ~$0.02/GB vs RAM ~$2+/GB), not algorithm; trade-off is higher latency/lower QPS. Also in this tier: turbopuffer, LanceDB (scale-to-zero when idle). (Slide 12/56)

- **HNSW (Hierarchical Navigable Small World)** — graph-based, multi-layer skip-list ANN index; default choice in 2026 because it achieves 95%+ recall at ~10ms in-memory. Default params: ef=200, m=16. Native in Pinecone, Weaviate, Qdrant, Milvus. Limits (explicit): RAM-bound (>10M vectors @768d costs ~10GB), poor for update-heavy corpora (rebuild is slow), not ideal for static billion-scale (→ DiskANN instead). (Slide 13/56)

- **HNSW vs IVF vs DiskANN** — three ANN index families compared: HNSW (graph in-memory, 95%+ recall @~10ms, ~1KB/vector RAM at 768d fp32, best for ≤10M hot latency-critical vectors); IVF/FAISS (cluster-based inverted index, lower RAM but higher latency ~30–50ms, needs retraining on large data drift, best for batch-mode static corpus / CPU-only infra; params nlist=1024, nprobe=64); DiskANN (graph on SSD, billion-scale on one node, ~30ms @99% recall, 10–50× cheaper than HNSW at scale, used by Pinecone serverless/pgvectorscale/Azure Cosmos DB, best for >100M vectors, cost-sensitive). RaBitQ (SIGMOD 2024 Best Paper): unbiased binary quantization for DiskANN, integrated in pgvectorscale & VectorChord, cuts RAM another 32× at comparable recall. (Slide 14/56)

- **Quantization** — memory-saving technique: float32 (4B/dim, 100% recall baseline) → int8 scalar (1B/dim, ~99% recall, 4× smaller) → binary (1 bit/dim, 95–98% recall, 32× smaller). Example: 100K vectors × 1536d: fp32=900MB → int8=225MB → binary=28MB. Asymmetric Quantization (Qdrant 1.15): store binary (cheap) but query with scalar precision — best of both, ≥99% recall at binary storage cost. Production default 2026: enable quantization before ingest, not after (re-quantize = re-index, needs blue-green deployment). (Slide 15/56)

- **Hybrid Search (BM25 + Vector + RRF)** — combines sparse/exact-term match (BM25/SPLADE) with dense/semantic match (Vector ANN/HNSW), merged via Reciprocal Rank Fusion (k=60). Production 2026 default: hybrid wins, Recall@10 ~10–15pp higher than dense-only (measured on your golden set), +6ms latency (parallel), 1.4× storage. Native in Qdrant, Weaviate, OpenSearch, Milvus. SPLADE gives higher recall than BM25 but needs GPU. (Slide 16/56)

- **Reciprocal Rank Fusion (RRF)** — score(d) = Σ 1/(k + rank_r(d)), k=60; rank-only fusion — no need to normalize raw scores between BM25 (TF-IDF) and cosine similarity. (Slide 16/56)

- **Filtered Search** — three approaches: Post-filter (ANN first, then filter results — recall silently collapses with no error, worse as filter tightens); Pre-filter/brute force (filter first, scan whole subset — correct but loses the index, latency scales with subset size); Filtered-ANN (index natively aware of filter — Qdrant filterable HNSW payload index, Milvus partition key, pgvector 0.8 iterative scan that auto-expands until k rows found). Key insight (explicit): filtering breaks HNSW graph connectivity ⇒ the graph "gets lost" and returns few/poor results; mandatory test = run the golden set with a highly selective filter (~1% of corpus match) — that's where the system breaks, not on an empty query. (Slide 17/56)

- **Late Interaction (ColBERT → ColPali)** — contrasts with single-vector embedding (whole chunk compressed to one vector, token detail averaged away). Late interaction keeps a vector per token/patch and scores via MaxSim: score = Σ_{t∈q} max_{d∈D} cos(t,d) — each query token finds its best-matching document fragment, capturing detail single-vector misses. ColPali: encodes PDF page images directly (SigLIP-So400m) — no OCR needed; 32×32 grid = 1024 patches/page, each 128d; handles tables/charts/scanned forms without preprocessing. Model family: ColQwen2.5, ColSmolVLM, ColInternVL. Cost caveat: quality costs storage — 1M pages × 1024 patches × 128d × 4B ≈ 524GB (down to ~30–60GB after quantization); requires vector DBs with multi-vector + MaxSim support (Qdrant, Milvus). (Slide 18/56)

- **RAG Pipeline (end-to-end)** — Documents → Chunking (512 tokens, 50 overlap) → Embedding (text-embed-3 / bge-m3) → Vector DB; separately User Query → Query Embed → Retrieve Top-K (with metadata filter, e.g. source/date≥2024) → LLM Generate. (Slide 19/56)

- **Chunking Strategies** — four explicit strategies: Fixed-size (512 tokens, baseline, may cut mid-sentence); Recursive (LangChain RecursiveCharacterTextSplitter, respects sentence/paragraph boundaries); Semantic (similarity-based, breaks at topic shift — slower but best quality); Hierarchical (parent=page, child=paragraph; retrieve child, return parent). Production tuning: chunk size 200–500 tokens for RAG, 1K+ for long-context; overlap 10–20% (~50–100 tokens); tooling: LangChain, LlamaIndex, Unstructured.io; Vietnamese should tokenize at sentence level, not byte-split. Explicit claim: Recall@k improves significantly switching fixed→semantic on benchmarks — "bad chunking makes even good embeddings useless." (Slide 20/56)

- **RAG Production Best Practices** — Retrieval hyperparameters: Top-K 5–10 for RAG (20–50 before reranker), ef_search (HNSW) default 200 (raise for recall), MMR diversity λ=0.5 to reduce duplicate chunks, metadata filter (not "filter early" — see Filtered Search). Production gotchas: embedding model must match between train and inference; query rewriting (HyDE, multi-query expansion); embedding versioning + zero-downtime re-index; monitor embedding drift weekly. (Slide 21/56)

- **2-Stage Retrieval (Recall + Rerank)** — Stage 1 Recall (fast): ANN returns top-100 candidates via bi-encoder (query & doc embedded separately), latency <20ms, high recall. Stage 2 Precision: cross-encoder scores relevance per (query,doc) pair jointly, selects top-10 highest quality. Rerankers 2026: self-host+GPU (bge-reranker-v2-m3, Jina v3, Qwen3-Reranker, ~50–200ms) vs managed API (Cohere Rerank v4, zerank, ~600ms, no GPU needed) — reranking adds directly to P99 latency. Embedding hosting options: self-host (sentence-transformers on GPU, more control, cheaper at scale) vs API (OpenAI text-embedding-3-small, Cohere embed v4+Rerank 3.5, simpler/faster to deploy). (Slide 22/56)

- **Context Rot / Long-context vs RAG** — Chroma Research (07/2025) study across 18 frontier models extending Needle-in-a-Haystack: quality degrades as input length grows (even on simple tasks, degradation uneven across models); for 1M-token-window models, the effect is commonly visible around 300–400K tokens; multi-hop/synthesis tasks break down much earlier; degradation depends on question similarity, noise, structure — exactly the variables retrieval controls. Economic argument: stuffing whole corpus into context pays for the entire corpus every request; retrieval pays for indexing once and each query only pays for the selected portion — the cost gap multiplies with QPS, which is why RAG persists. 2026 default: hybrid — retrieve 50K–200K relevant tokens, then let long-context model reason over that (not an either/or choice); "large window is capacity, not a guarantee." (Slide 23/56)

- **GraphRAG / Knowledge Graph** — contrasted with vector RAG: Vector RAG retrieves top-K nearest chunks by cosine similarity ("relevant paragraphs"); GraphRAG models entity-relation graphs and can multi-hop traverse (e.g., PayPal→Alice→Project X→Bob→Mahle) in microseconds. GraphRAG wins on questions like "Who at PayPal collaborated with someone hired by Mahle?" — vector RAG can only return chunks about PayPal OR Mahle separately, no cross-document multi-hop. Use cases: P3C diabetes copilot (Memgraph, patient journey + drug interactions), Alzheimer research (1.6M edges genes-drugs-trials), M&A intelligence (GlassDollar/Siemens/Mahle, entity search across millions of companies). Rule of thumb (explicit): choose graph when the answer is a relationship, not a text passage. (Slide 24/56)

- **GraphRAG Construction Pipeline** — Documents (text corpus) → NER (spaCy/LLM) → Entity Linking (dedupe & canonical IDs) → Relation Extraction (e.g., (Alice, worked_on, Project X)) → Community Detection (Leiden algorithm, sub-graph clusters) → Indexed KG (Neo4j/Memgraph). Tooling: MS GraphRAG (community summaries, high quality, most expensive to index), LazyGraphRAG (defers extraction to query-time, index cost ≈ vector RAG), LightRAG/Fast GraphRAG (lightweight index), Neo4j (Cypher) / Memgraph (in-memory, sub-ms traversal). 2026 default architecture — Vector+Graph Layered: (1) start with vector RAG for conversational grounding, (2) add KG for entity-dense domains (legal, medical, M&A), (3) hybrid: vector retrieve → KG expand → LLM, (4) cost: full extraction is 5–20× vector RAG cost; Lazy ≈ vector RAG cost. Explicit note: cost dynamic "reversed" in 2026 — LazyGraphRAG index cost ≈0.1% of full GraphRAG, so "graph too expensive to try" is no longer valid; choose by question shape, not index budget. (Slide 25/56)

- **Agentic Retrieval** — contrasted with Classic RAG (single pass: embed query → top-K → generate, for simple lookups). Agentic retrieval: the agent decides how to retrieve — analyzes complexity, splits multi-part questions, chooses sources, retrieves across multiple rounds. Loop: (1) understand query — simple or multi-step? (2) plan — which sources, what order (3) retrieve — vector/BM25/KG/SQL/API (4) reflect — is evidence sufficient? (5) repeat if not, then generate answer. Cost: extra LLM call ⇒ added latency + tokens; not the default for every query. Infrastructure trend: Weaviate 1.37 (2026) embeds an MCP server at /v1/mcp on the same port as REST API — agents can query/write directly, no separate integration layer; the vector DB is no longer just a backend library but an agent-callable tool (cross-ref Day 9: MCP). (Slide 26/56)

- **Agent Memory** — framed as "the two stores from today": online store answers "what do we know about this user" (<10ms); vector store answers "what was said before that's relevant." Three 2026 architectures: Mem0 (vector-first, extracts "facts" from conversation), Zep (temporal knowledge graph via Graphiti), Letta/ex-MemGPT (3 tiers: core/recall/archival). Benchmarks: LoCoMo, LongMemEval, BEAM. (Slide 27/56)

- **Semantic Cache** — cheapest cost lever: if a new query is close to a cached one (cosine > threshold), return the stored answer instead of calling the LLM. AWS measurement on 63,796 real queries (threshold 0.75): inference cost down up to 86%, latency improved 88% on cache hits, accuracy held ~91%. Explicit warning: a wrong cache hit is more dangerous than no cache. Four failure modes: context-dependent queries (same text, different needed answer), time-sensitive queries (stale answer served), changing embedding model invalidates the whole cache (same re-index trap), caching a hallucinated answer and serving it repeatedly. Similarity threshold must be measured, not guessed. (Slide 27/56, code detail Slide 30/56)

- **Semantic Cache implementation (code-level)** — `cached_answer(user_id, q, threshold=0.75)`: embed query, search cache filtered by tenant namespace (never share across tenants), if hit score ≥ threshold return cached payload (HIT), else call LLM with built context (MISS) and upsert with `ttl=3600` (must expire). Three parameters, three failure classes: threshold too low → wrong answer served (must measure, AWS uses 0.75); missing ttl → stale answers persist forever; missing namespace → user A receives data from user B's cached answer — this is a security hole, not a cache bug. Changing the embedding model requires wiping the cache entirely (old/new vectors are not in the same space). (Slide 30/56)

- **Retrieval as an Agent Tool** — a tool schema example (`SEARCH_TOOL`) with `name`, `description`, `input_schema` (query string, product enum, top_k default 8). Four things that determine tool quality: (1) `description` IS the retrieval prompt — the agent decides whether/when to call based only on this text; ambiguity causes wrong-time calls; (2) filter fields should be enums, not free strings, so the agent can't invent invalid values; (3) return citations + score, not just text, so the LLM (and the developer) can trace sources; (4) `top_k` must have a cap, or the agent dilutes its own context. (Slide 28/56)

- **Feature Store** — a system that centralizes ML feature computation/storage so features are reused across models and computed consistently between training and serving. Components: Feature Registry (metadata catalog), Offline Store (S3/BigQuery — batch features, full history, seconds–minutes latency, used for training), Online Store (Redis/DynamoDB — <5–10ms lookup, current value only, used for inference), and `materialize` (batch loads offline → online). "Single source of truth = no skew." (Slide 36/38)

- **Point-in-Time (PIT) Join** — when building a training set, retrieve the feature value as-of the timestamp of each event, never a future value. Feast's `get_historical_features(entity_df)` performs this PIT join on the offline store. Mistake: using the LATEST value causes data leakage ⇒ production accuracy 20–30% lower than training accuracy. (Slide 38/56)

- **Training-Serving Skew** — feature computed differently between training and serving, degrading model performance in production with no obvious error. Example 1 (Aggregation): training uses `pd.DataFrame.mean()` over full history, serving uses `running_mean(last_N)` over only N recent records ⇒ different values, model drifts. Example 2 (Date parsing): training parses UTC, serving parses local timezone ⇒ "hour of day" feature is off by 7h (Vietnam). Feature Store fix: one single feature definition used for both training and inference — no separate code paths. (Slide 40/56)

- **On-Demand Feature View** — computes a feature at request time by combining stored features with request-time data (e.g., transaction `amount`, which doesn't exist at materialize time) using the same formula for both training and serving. `RequestSource` supplies request fields; `@on_demand_feature_view(sources=[stored, request], mode="python")` defines the combining function. `write_to_online_store=True` computes on write; default `False` computes on read. (Slide 34/56)

- **Streaming Feature Pipeline** — OLTP DB (Postgres) → CDC (Debezium) → Kafka topic (raw events) → Flink/Spark Stream (tumbling/sliding window) → Online Store (Redis), with a parallel path to Offline Store (S3/Delta). Patterns: CDC (every row UPDATE → Kafka event), Aggregate (transaction velocity 5min/1h window), Feast Push API (app pushes event directly to online store). Needed for: fraud detection, dynamic pricing, real-time recsys. Not needed for: churn prediction (daily batch OK), credit scoring. (Slide 41/56)

- **Embedding as a Feature (`vector_index` in Feast)** — an embedding can be declared as a `FeatureView` field with `vector_index=True`, `vector_search_metric="COSINE"`, retrieved via `store.retrieve_online_documents_v2(...)` by similarity instead of by key. Same FeatureView API, registry, and TTL semantics as tabular features, but lookup is by similarity. Practical effect: a RAG corpus becomes a feature view with schema, lineage, versioning, and PIT semantics. Config example: `online_store: type: milvus, vector_enabled: true`. Status: Alpha, supports Milvus, SQLite, Qdrant, PGVector. (Slide 44/56)

## 2. Relationships & Mechanisms

- **Embedding → Vector DB → ANN + Hybrid → RAG → GraphRAG → Agentic & Memory → Feature Store → Production** — the deck's stated overall agenda/dependency chain (Slide 2/56). Each stage builds on the prior: you need embeddings before a vector DB is meaningful; ANN indexing/hybrid search are the retrieval mechanism inside RAG; GraphRAG and agentic retrieval extend RAG for relationship-questions and multi-step retrieval; feature stores and production concerns (security, cost) wrap around the whole system.

- **Metric choice depends on / must match pretraining objective** — using cosine vs dot vs Euclidean incorrectly against how the model was trained degrades recall by 10–20% (explicit). (Slide 8/56)

- **Filtering breaks HNSW's graph connectivity** — filtered search is not simply "ANN then filter" or "filter then scan"; naive approaches (post-filter, pre-filter) trade off recall collapse vs. losing the index's speed benefit; filtered-ANN designs (payload-aware HNSW, partition keys, iterative scan) are required to avoid this trade-off. Mechanism: pre-filtering narrows the graph's traversable neighborhood so the graph "loses its way." (Slide 17/56)

- **Quantization trade-off** — Input: full-precision vectors (float32) → Process: reduce bit-width per dimension (scalar int8 or binary) → Output: smaller index, small recall loss. Asymmetric quantization (store binary, query with scalar precision) resolves most of the trade-off. Enabling quantization is a re-index operation, so it must be planned before ingest or via blue-green deployment. (Slide 15/56)

- **Hybrid Search mechanism** — Input: query → Process: run BM25/SPLADE (sparse) and Vector ANN (dense) in parallel, merge ranked lists via RRF (rank-based, no score normalization needed) → Output: top-K hybrid results. Why RRF: BM25 TF-IDF scores and cosine scores are not on comparable scales, so rank-based fusion avoids the normalization problem. (Slide 16/56)

- **RAG pipeline mechanism** — Input: Documents → Chunking → Embedding → stored in Vector DB (indexing path); separately, Input: User Query → Query Embed → Retrieve Top-K (with metadata filter) → Output: LLM Generate (query path). Chunking strategy is called out as determining "80% of RAG quality" — poor chunking undermines even a good embedding model. (Slides 19–20/56)

- **2-stage retrieval depends on 1-stage recall** — bi-encoder (Stage 1) trades precision for speed to get a wide candidate pool (top-100); cross-encoder (Stage 2) trades speed for precision by scoring query+doc jointly on the smaller candidate set. This is a prerequisite relationship: reranking without a good Stage-1 recall set can't recover missed documents. (Slide 22/56)

- **Long-context models don't replace RAG; they combine** — the "large context window" capability doesn't remove the need for retrieval because (a) quality still degrades with input length (context rot) and (b) retrieval is economically cheaper per-query at scale (index once, pay per selection, vs. paying for the full corpus every request). The 2026 default combines both: retrieve first (50K-200K tokens), then reason with long-context. (Slide 23/56)

- **Vector RAG vs GraphRAG trade-off** — Vector RAG: fast, cheap to index, good for "relevant passage" questions; poor at cross-document multi-hop questions because it retrieves chunks about entities separately, without connecting them. GraphRAG: expensive to fully index (unless using Lazy variants), but resolves multi-hop relationship queries in microseconds via graph traversal. Layered architecture (vector first, add KG for entity-dense domains, hybrid vector→KG→LLM) is the recommended production pattern, not "GraphRAG replaces vector RAG." (Slides 24–25/56)

- **Agentic retrieval depends on / enables** — depends on having retrieval as a callable tool (with well-specified description, enum filters, citations, top_k cap — Slide 28) and enables multi-step, multi-source retrieval loops (plan → retrieve → reflect → repeat) that classic single-pass RAG cannot do; trade-off is added LLM-call latency/cost, so it is not the default for simple queries. (Slides 26, 28/56)

- **Feature Store resolves Training-Serving Skew** — mechanism: define feature computation once (in a FeatureView/on-demand transform) and reuse identically for both the training pipeline (via offline store + PIT join) and the inference service (via online store lookup) → eliminates divergent code paths that caused skew (e.g., `mean()` vs `running_mean()`). (Slides 36, 40/56)

- **Feast materialize pipeline** — Input: Offline Store (S3/BigQuery, batch, full history) → Process: `feast materialize` / `materialize-incremental` (batch load) → Output: Online Store (Redis/DynamoDB, current value only, <5–10ms lookup). Batch features: daily update sufficient; streaming features: need sub-second freshness via CDC/Kafka/Flink or Feast Push API instead of materialize. (Slides 36–37, 41/56)

- **On-demand feature view mechanism** — Input: stored feature (e.g., `avg_amount_7d`, precomputed) + request-time data (e.g., `amount`, only known at request time) → Process: apply the same combining formula (e.g., `amount / avg_amount_7d`) → Output: `amount_vs_avg` feature, computed identically whether for training or serving. Prerequisite: the underlying stored feature must already exist via a normal FeatureView. (Slide 34/56)

- **Feature Store and Vector Store convergence** — Feast 0.65 lets the online store itself be a vector DB (Qdrant, Milvus, FAISS) alongside Redis/DynamoDB/Cassandra/Postgres, meaning one registry can serve both tabular features (e.g., `txn_count_7d`) and embedding feature views (vector user/item) for the same model, through the same online lookup, same PIT join, same anti-skew guarantee. Framed explicitly as: "RAG needs personalized context (feature), and classical ML increasingly uses embeddings as features — don't build two parallel systems if one suffices." (Slide 43/56, code Slide 44/56)

- **Personalization + Grounding combined (build_context pattern)** — Input: user_id + question → Process: (1) online feature lookup answers "who is this user" (<10ms) → (2) vector search + language filter answers "what is relevant" → (3) personalize the prompt, THEN ground it with retrieved docs → Output: composed LLM prompt. Explicit warning: "personalization without grounding = confident hallucination; grounding without personalization = correct but soulless." Feature lookup (<10ms) is near-free relative to an LLM call, so it should not be skipped for cost reasons. (Slide 29/56)

- **CodeWiki links back to GraphRAG** — code is inherently a graph (functions call functions, modules import modules, classes inherit classes); "what breaks if I change this function?" is a multi-hop question — the class vector RAG handles poorly and graph traversal handles well. Good CodeWiki = vector search (find relevant snippet) + call graph (trace dependencies). (Slide 52/56)

- **DocWiki chunking is an organizational-layer decision** — how you write/structure your own docs (llms.txt, self-contained pages, markdown) determines how well *other systems'* retrieval will chunk and answer questions about your product — poor doc structure ⇒ meaningless chunks ⇒ wrong agent answers about your product. (Slide 53/56)

- **Cost levers ranked by effectiveness (explicit ordering)** — 5 cost components: (1) embedding (one-time for corpus + daily delta), (2) index storage (dims × bytes × vector count, after quantization), (3) query compute (QPS × storage tier), (4) reranker (per-query, adds to P99), (5) LLM generation (usually the largest). 5 levers in order of effectiveness: (1) semantic cache (cuts both #4 and #5), (2) quantization (int8 4×, binary 32× off #2), (3) choosing the right storage tier (object storage for low-query corpora), (4) Matryoshka (cuts dims, cuts RAM), (5) smaller top-K (fewer tokens into LLM). Unbudgeted cost (explicit warning): re-index — changing embedding model repays all of cost #1 and temporarily doubles cost #2 during blue-green; treat as a recurring cost, not an incident. (Slide 48/56)

## 3. Examples & Distinctions

- **HNSW vs IVF vs DiskANN**: similarity — all are ANN index structures for vector search. Difference/criterion — HNSW: in-memory graph, best recall/speed for ≤10M hot vectors, RAM-bound; IVF: cluster-based inverted index, lower RAM/higher latency, needs retraining on drift, good for static CPU-only batch workloads; DiskANN: graph-on-SSD, billion-scale on one node, 10–50× cheaper than HNSW at large scale. Distinguishing criterion: choose by corpus size + latency budget + RAM budget. (Slide 14/56)

- **Post-filter vs Pre-filter vs Filtered-ANN**: similarity — all combine metadata filtering with vector search. Difference — post-filter (ANN first, filter after) silently collapses recall with tight filters (no error raised); pre-filter (brute-force scan of filtered subset) is always correct but loses the index and scales latency with subset size; filtered-ANN (index natively filter-aware) avoids both failure modes. Distinguishing criterion: whether the filter is applied before/after/inside the ANN traversal. (Slide 17/56)

- **Single-vector vs Late Interaction (ColBERT-style)**: similarity — both encode text into vectors for retrieval. Difference — single-vector compresses a whole chunk into one vector (averages away token detail); late interaction keeps one vector per token/patch and scores via MaxSim, capturing fine-grained matches single-vector misses, at higher storage cost. (Slide 18/56)

- **Classic RAG vs Agentic Retrieval**: similarity — both retrieve context to ground an LLM answer. Difference — classic RAG is a single pass (embed → top-K → generate), good for simple lookups; agentic retrieval lets the agent analyze complexity, split multi-part questions, choose sources, and retrieve iteratively — at the cost of extra LLM calls/latency. Distinguishing criterion: whether retrieval is a fixed one-shot step or an agent-driven decision loop. (Slide 26/56)

- **Vector RAG vs GraphRAG**: similarity — both retrieve context for LLM grounding. Difference — vector RAG surfaces "relevant passages" via nearest-neighbor chunk similarity; GraphRAG surfaces "relationships connecting multiple entities" via graph traversal, needed for cross-document multi-hop questions vector RAG cannot answer. Distinguishing criterion: is the answer a relationship (→ graph) or a passage (→ vector)? (Slide 24/56)

- **Offline Store vs Online Store**: similarity — both hold feature values for the same features. Difference — offline store (Parquet/S3/Delta/Iceberg/Snowflake/BigQuery/Redshift) holds full history, batch access, seconds-minutes latency, used for training; online store (Redis/DynamoDB/Cassandra/Aerospike) holds only the current value, per-entity KV lookup, <10ms P99, used for serving. Feast's `materialize()` loads offline → online. (Slide 38/56)

- **Feast vs Tecton vs Hopsworks**: similarity — all are feature stores solving reuse/consistency/latency. Difference — Feast: open-source (LF AI&Data), self-hosted, full control, best for small–medium teams; Tecton: managed, real-time features with automatic DAG scheduling, enterprise SLA/RBAC/lineage, best for ML-heavy teams with strict latency SLAs; Hopsworks: on-prem+cloud, Spark+Flink streaming integration, GDPR-ready lineage/versioning, best for regulated industries (banking, healthcare). Databricks Workspace Feature Store is explicitly called legacy (2024) — migrate to Feature Engineering in Unity Catalog. (Slide 39/56)

- **ML Era (2015–2022) vs LLM Era (2023–2026) for vector/feature stores** (explicit comparison table): Vector store role shifts from candidate generation for recsys/face-image search → RAG retrieval/agent memory/semantic cache. Embeddings shift from task-specific per-app models (FaceNet, two-tower, doc2vec) → foundation models reused across use cases (OpenAI, BGE, Voyage). Index tooling shifts from embedded FAISS/Annoy/NMSLIB inside the app process → managed multi-tenant services (Pinecone, Zilliz Cloud, Vertex Vector). Feature stores shift from purely tabular features → tabular plus embedding feature views with on-demand transforms for prompt context. Freshness shifts from daily/hourly batch default (streaming only for fraud) → sub-second streaming as the baseline for fraud/pricing/real-time recsys. (Slide 50/56)

- **Fraud Detection vs Recommendation Systems vs Dynamic Pricing** (feature-store use cases): Fraud (PayPal, Wise) — <10ms/transaction latency, velocity+device fingerprint+amount-vs-7d-avg features, streaming freshness (Kafka→Redis), Tecton+Redis or Feast+Aerospike. Recsys (DoorDash, Spotify) — <50ms latency, user embedding+last-N interactions+item popularity, hybrid freshness (daily batch + last-click stream), Tecton (DoorDash, Atlassian) or Hopsworks (regulated). Dynamic pricing (Uber, Grab) — <100ms latency, demand surge+supply+competitor price+time-of-day, sub-second freshness, Tecton DAG. Common takeaway: feature stores win simultaneously on reuse + train/serve consistency + low-latency lookup — no other tool solves all three. (Slide 42/56)

## 4. Assumptions, Boundaries & Gaps

- **Golden set is the final arbiter** — repeated explicit principle: benchmark rankings (MTEB, VN-MTEB) don't transfer directly to your domain; must re-rank/measure on your own golden set before trusting a model choice (mentioned re: embedding model selection, chunking strategy, hybrid search gains, similarity thresholds). - **Changing embedding model = full re-index** — stated as a recurring, unavoidable cost across multiple contexts (model selection, MRL, RAG production, semantic cache, cost accounting) — not a one-time migration cost but something to budget periodically. (Slides 6, 21, 30, 48/56)

- **Filtered search recall collapse is silent** — no error is raised when post-filter recall collapses; this is called out explicitly as a dangerous edge/failure case that requires proactive testing (golden set + high-selectivity filter), not something surfaced by normal operation. (Slide 17/56)

- **VN-MTEB limitation (explicit, source-stated)** — VN-MTEB is translated from English MTEB, so it measures language capability but not Vietnamese cultural/domain knowledge — an acknowledged gap in the benchmark itself. (Slide 7/56)

- **Context Rot thresholds are approximate, not guaranteed** — the ~300–400K token degradation point is described as "commonly observed" across an 18-model study, not a fixed universal boundary; degradation is explicitly stated to vary by model and be worse for multi-hop/synthesis tasks. (Slide 23/56)

- **llms.txt is not a formal standard** — explicitly noted as "not yet an IETF/W3C standard, still a community proposal," despite being defaulted-on by Mintlify, Fern, GitBook, Vercel, Supabase. (Slide 53/56)

- **Semantic cache correctness depends on unproven threshold generalization** — the 0.75 threshold and 86%/88%/91% figures are from one AWS study on 63,796 queries; the deck explicitly instructs "must measure, don't guess" for your own deployment — implying the given numbers are not guaranteed to transfer. (Slides 27, 30/56)

- **Security/compliance boundaries (OWASP LLM08:2025)** — three named risks: embedding inversion (original text can be reconstructed from vectors — embeddings are not anonymization), cross-tenant leakage (metadata-filter isolation is "soft" — one filter bug leaks everything), retrieval poisoning (malicious documents injected into corpus to steer answers). Right-to-erasure conflicts with immutable ANN indexes: a deletion request must propagate to the vector index + all materialized online-store rows + semantic cache; deletion path must be designed before ingest, not after.
