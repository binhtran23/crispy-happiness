# Core Knowledge

Source: `day14-ai-evaluation-benchmarking_E403.pdf` — AI Evaluation & Benchmarking (AICB-P1, Ngày 14). Slide references use the deck's own numbering "X / 101" (101 content slides across 120 PDF pages; extra PDF pages are animation/build steps of the same slide).

## 1. Core Concepts

- **Evaluation (evals)** — Explicit. The scientific method applied to AI quality: Hypothesis → Experiment (run benchmark) → Measure (numeric score) → Conclude (evidence-based). Turns "agent feels good" into a repeatable, comparable, gate-able number. (Slide 4)
- **Eval-Driven Development (EDD)** — Explicit. Evals play the role unit tests played for deterministic code: write evals first to define "correct," then optimize prompt/model. Needed because agents are probabilistic + multi-step (same input → different output each run), so `assert output == expected` breaks; grading targets outcome/behavior, not exact match. Principle: "Grade what the agent produced, not the path it took" — forcing exact step order is brittle since agents find valid paths humans didn't anticipate. (Slide 5)
- **Eval Maturity Ladder (Husain & Shankar)** — Explicit. L0 Vibe-checks (manual read of a few outputs — only trustworthy when the builder is the domain's power user; "impractical/dangerous" for complex apps) → L1 Error analysis + offline evals (code-based + LLM-as-judge) → L2 EDD gating releases (eval must pass before deploy). Recommended start: manually review 20–50 real outputs before building any eval infrastructure. (Slide 6)
- **Four operating axes of eval** — Explicit (Evidently's taxonomy): Offline (fixed dataset, run in dev/CI-CD = the lab's release gate, regression tracking), Online (live traffic, continuous monitoring, bridges to Day 13 OTel traces as substrate), Guardrails (inline, blocks before response reaches user — blocks rather than just measuring), Human-in-the-loop (expert review of sampled outputs — the 4th axis, calibrates the other three). Offline alone misses production quality; human alone doesn't scale — need combination. (Slide 7)
- **Outcome vs Trajectory grading** — Explicit. Outcome = final state of the environment (e.g., does a reservation row exist in the DB). Trajectory = the full step-by-step trace (every tool call, reasoning, intermediate result). Analogy: grading a surgeon — outcome is patient recovery, but trajectory (how the surgery was done) is still reviewed. Priority: grade the outcome, read the trajectory to understand why. (Slide 8)
- **Golden dataset** — Explicit. QA pairs reviewed by subject-matter experts (SME); covers all main use cases; has difficulty levels (easy/medium/hard); includes edge/adversarial cases; each item tagged with metadata (use case, difficulty, slice). It is the ground truth of your eval — if the expected answer is wrong/ambiguous, the whole evaluation is misleading. Silver→gold pipeline: synthetic silver → SME review/bias audit → gold; disagreements must be resolved before inclusion. (Slide 28)
- **Synthetic Data Generation (SDG)** — Explicit. LLM generates candidate questions rapidly from your own documents (hundreds in minutes) to solve the golden-dataset bottleneck (hand-writing cases is slow). Generation is the easy part; **filtering** (dropping trivial, unanswerable, or distribution-skewed items) is the real product. SDG does not replace the golden dataset — it produces silver candidates for faster human review, not direct benchmark inclusion. (Slide 32)
- **Retrieval evaluation metrics** — Explicit. Two families: order-unaware (Hit Rate@k, Recall@k, Precision@k — care only about the top-k set) and order-aware (MRR, MAP, NDCG@k — position-weighted, correct doc ranked lower = penalized more). See formulas in Relationships/Mechanisms. Framed as "retrieval is the ceiling of RAG quality" — a retriever miss means the generator cannot rescue the answer. (Slides 23–27)
- **North Star / Guardrail / Diagnostic metrics** — Explicit. North Star: one metric reflecting core user/business value (e.g., task success rate). Guardrail: must-not-regress metrics (faithfulness, p95 latency, cost/request) — violation blocks release. Diagnostic: used only to debug why North Star dropped (context recall, tool-call accuracy, refusal rate) — never the optimization target itself, or it becomes a Goodhart trap. (Slide 18)
- **Lexical vs embedding vs LLM-judge metrics (metric maturity)** — Explicit, three-tier: (1) Lexical/string metrics (Exact Match/F1, BLEU, ROUGE-L, WER) — cheap, deterministic, but meaning-blind; fail badly on negation ("should refund" vs "should not refund" scores as near-identical). (2) Embedding/cosine similarity — catches paraphrase but falls into the "Contradiction Trap": two opposite-meaning sentences can still have cosine > 0.90 because they share topic/vocabulary. (3) LLM-as-Judge (+ NLI) — needed to actually judge correct/incorrect. (Slides 19–20)
- **RAG metrics pipeline (Question → Retriever → Context → Generator → Answer)** — Explicit. Context Recall (retriever stage) — did we retrieve enough evidence; low = missing info. Context Precision (retriever stage) — is retrieved context ranked well / not noise-diluted. Faithfulness (generator stage) — is the answer grounded in context; low = hallucination. Answer Relevancy (generator stage) — does the answer address the question; low = off-topic. (Slide 22)
- **LLM-as-Judge** — Explicit. A judge LLM receives question + agent answer + reference answer + rubric, and returns a score (e.g., 1–5) with rationale (rationale required for debuggability). MT-Bench (Zheng 2023) found strong judges reach ≈85% agreement with humans, comparable to or exceeding human-human agreement (≈81–82%), while scaling far beyond manual review. (Slide 55)
- **Rubric design** — Explicit. Good rubric: concrete per-level criteria (e.g., 5=correct/complete/grounded, …, 1=wrong/unsupported), explicit "length is NOT a factor," and forces the judge to reason before scoring (Reasoning field before Score field). Vague rubrics → inconsistent scores. (Slide 56)
- **Pointwise vs Pairwise judging** — Explicit. Pointwise: absolute score per answer against a rubric; stable (reordering flips only ≈9% of cases), easy to threshold for a release gate, but weak at distinguishing near-equal answers. Pairwise: judge picks which of A/B is better; tracks human preference more closely but less stable (reordering flips ≈35%), sensitive to position/distraction bias. (Slide 57)
- **LLM-judge bias (quantified)** — Explicit, from CALM's bias taxonomy (12 types total; deck covers 3): Position bias (judge favors the answer shown first — GPT-3.5 deviates ≈50%, Claude-v1 up to ≈75%; fix: swap order and average). Verbosity bias (judge prefers longer answers; a repeated-list attack fools weak judges 91.3% of the time vs 8.7% for GPT-4; fix: rubric explicitly bans length as a factor). Self-preference bias (judge favors same model family — GPT-4 ≈+10%, Claude-v1 ≈+25% win rate, model-dependent; fix: use a judge from a different model family). (Slide 58)
- **De-biasing techniques (5, mandatory)** — Explicit: (1) Swap order and average — kills position bias. (2) Force rationale + CoT before scoring — improves reliability. (3) Rubric + multi-dimension scoring — scores each criterion separately, blocks verbosity bias. (4) Calibrate against human judgments. (5) Multi-judge jury (different model families) — reduces self-preference bias. Anti-pattern: trusting a single uncalibrated judge's number absolutely. (Slide 59)
- **Calibration (Cohen's κ / Krippendorff α)** — Explicit. Report chance-corrected agreement between judge and human on a labeled set — not raw accuracy. Example: GPT-4 judge vs human on TriviaQA κ≈0.84 (close to but below the human-human ceiling κ≈0.97). Measure κ per slice (use case, difficulty) — aggregate agreement can hide a badly-wrong slice. An uncalibrated judge is "not evidence, just an expensive opinion." (Slide 60)
- **PoLL — Panel of LLM Judges (Verga 2024)** — Explicit. A panel of small, cheap, different-family judges is ≈7× cheaper than one large frontier judge and their biases cancel out, correlating with human judgment better than a single large judge. Mechanism: ≥2 different-model judges vote (majority for binary, average for 1–5) → compute agreement rate → on conflict, call one frontier model as tie-breaker only when needed (to save cost). Cheap judges tend to be more lenient — don't trust a single judge 100%. This is the lab's Consensus Engine mission. (Slide 62)
- **RAGAS framework (v0.4.3)** — Explicit. A metrics library for RAG and agent evaluation. Must pin `ragas==0.4.3` (released 2026-01-13, Python ≥3.9) — API changed substantially from v0.1 (RAG-only) through v0.2 (`SingleTurnSample`+`EvaluationDataset`, capitalized metric classes) to v0.4 (new `ragas.metrics.collections` namespace, async scoring). Old import path `from ragas.metrics import Faithfulness` is deprecated (still resolves via `__getattr__` + warning but not in `__all__` — "importable" ≠ "exported"; will be removed in v1.0). New path: `from ragas.metrics.collections import Faithfulness`. (Slides 63–67)
- **RAGAS core 4 metrics** — Explicit. Faithfulness = supported claims / total claims (0–1); low = hallucination. ResponseRelevancy (alias AnswerRelevancy) = does the answer address the question; low = off-topic/generic. ContextPrecision = order-aware, Average-Precision-style ranking of relevant chunks; low = noisy/redundant context. ContextRecall = claim-based — % of reference-answer claims supported by retrieved context; low = missing retrieval evidence. Faithfulness computed via NLI: answer split into atomic claims, each checked for entailment by context; Faithfulness = (claims entailed) / (total claims). (Slides 65–66)
- **RAGAS agent/tool-use metrics** — Explicit (bridges to Day 9 Multi-Agent): ToolCallAccuracy (with ToolCallF1) — did the agent call the right tool with the right args; TopicAdherence — did the agent stay within its permitted topic scope; AgentGoalAccuracy (WithReference / WithoutReference variants) — did the agent complete the user's goal. (Slide 68)
- **Statistical rigor concepts** — Explicit. Confidence Interval (CI) — a score difference must be compared against the CI width, not read as a raw delta; at n=50, p=0.5, 95% CI ≈ ±14% (worst case). Wilson score / Bayesian Beta-Bernoulli — correct CI methods for small n (under a few hundred points); CLT/Wald normal approximation under-covers badly at small n (at n=30, "95%" CI actually covers only ≈60–75%). Paired comparison — run both versions on the *same* test cases and analyze the per-question difference; reduces variance of the difference (~1/3 reduction at correlation≈0.5), increasing statistical power versus comparing two independent means. McNemar's test — for paired binary (pass/fail) outcomes, only discordant pairs (b = old-pass/new-fail, c = old-fail/new-pass) carry information; use exact binomial test on discordant pairs when b+c < 25 rather than the χ² approximation. (Slides 70–73)
- **Determinism myth** — Explicit. temperature=0 does NOT guarantee identical output: ≈5–12% of prompts change their answer across seeds at temp 0 (greedy), due to floating-point/batching/parallelism effects; agentic pass@1 has std >1.5pp even at temp 0. A single "win" is not sufficient evidence; run multiple seeds and report mean ± std. (Slide 74)
- **Sample-size / statistical power** — Explicit. Detecting a small true delta needs far more cases than intuition suggests: ~969 paired cases to detect an absolute 3% delta at 80% power; ~246 for a ±5% margin at p=0.8; ~984 for a ±2.5% margin. A 50-case lab benchmark cannot prove a 3-point "win." (Slide 75, citing Miller 2024 "Adding Error Bars to Evals")
- **pass^k reliability metric** — Explicit. pass^k = probability an agent succeeds all k independent i.i.d. attempts at the same task = p^k (distinct from pass@k = at least 1 of k correct). At p=0.9 pass@1, pass^4≈66%, pass^8≈57% — reliability decays exponentially with required consistency. One good run proves nothing; need multi-run consensus + regression gate to catch instability. (Slide 48)
- **Eval economics** — Explicit. Human annotation costs $1–5+ per example (labor cost); LLM-as-Judge costs cents per example (token bill) — a unit-economics inversion. Report cost as $-per-eval. 2026 illustrative judge pricing (per 1M tokens, input/output): Gemini Flash-Lite ≈$0.10/$0.40 (cheapest), gpt-4o-mini (legacy) ≈$0.15/$0.60, Claude Haiku 4.5 ≈$1.00/$5.00, Sonnet 4.6 (frontier) ≈$3.00/$15.00 — mini/flash/haiku judges are ~5–30× cheaper than frontier. (Slides 77–78)
- **Prompt caching + Batch API discounts** — Explicit. Prompt caching (cache the stable rubric/system-prefix/few-shot; Anthropic cache-read ≈90% off, OpenAI ≈50–75% off cached input) stacks with Batch API (non-urgent eval work, 24h window, ≈50% off input+output — Anthropic Message Batches / OpenAI Batch API). Output tokens are not cached even in batch mode. Net realistic savings ≈30–50% on batchable eval workloads. Output tokens dominate cost (~4–5× input cost) — cap verbosity (short rationale / `max_tokens` limits) on cheap smoke runs; allow full CoT rationale only on release-gate runs (CoT improves accuracy). (Slides 79–80)
- **Async runner / concurrency** — Explicit. `RunConfig(max_workers=N)` in RAGAS fans out judge calls in parallel (defaults: max_workers=16, timeout=180, max_retries=10, max_wait=60, seed=42) — turns an hours-long eval suite into minutes. (Slides 69, 81)
- **Tiered sampling** — Explicit. Two-tier eval strategy: cheap/fast judge on a small "smoke" subset (≈15× cheaper per token than frontier, for catching trends and failing fast) plus a full-suite run on a frontier judge for the actual release gate and tie-breaking. Cheap judges have leniency bias (score fluent-but-wrong answers too highly). (Slide 82)
- **Eval Gate / Regression gate (CI/CD)** — Explicit. An eval gate is the "unit test" for a non-deterministic agent: runs a fixed eval suite on the golden set on every prompt/agent change, compares to baseline; PASS → deploy, FAIL → block merge. Ordinary unit tests don't catch LLM regressions (non-deterministic, multi-step output). Regression evals should aim for near-100% pass rate. (Slide 83)
- **Distribution-aware gating** — Explicit. Gating on the average pass rate alone can hide a severe regression concentrated in one subset/category (e.g., refund questions) — compare score distributions by category, new vs baseline, not just the aggregate mean. Statistical significance: p<0.05 (Welch t-test for continuous rubric scores, two-proportion z-test for binary). Effect size: |Δ| must exceed a noise floor (illustrative ≈0.03 on a 0–1 scale). Compare against a rolling 7-day baseline, store per-route JSON in Git. (Recipe attributed to vendor FutureAGI; thresholds are tunable starting points, not fixed standards.) (Slide 84)
- **Composite release score (quality + cost + latency)** — Explicit, framework "CLEAR": optimizing accuracy alone costs 4.4–10.8× more than an equivalent cost-aware choice; composite scoring predicts production performance far better than accuracy-only (correlation ρ=0.83 vs 0.41). Latency measured via TTFT (time-to-first-token, <1s = perceived instant) and TPS (tokens/sec, >~10 tok/s target). A single run's pass rate can look like 60% but drop to 25% once 8-run consistency is required — run each case N times and gate on the distribution, not one lucky run. (Slide 85)
- **Safe rollout: Shadow → Canary → Rollback** — Explicit. Shadow: mirror real traffic to the new version without serving its output to users (zero blast radius); compare baseline vs shadow output via cosine similarity, flag when <0.70. Canary: staged traffic ramp (illustrative 1%→10%→50%→100%, 3–10% starting tiers also common), each tier gated on eval/latency/cost/error thresholds. Guardrail breach at any tier triggers automatic rollback. (Slide 86)
- **Judge drift** — Explicit. Changing the judge model or its temperature changes scores, creating a "false regression" (raises the question: is it model regression or judge regression?). Mitigation: pin the judge model + temperature, version the rubric file in Git, bump the version explicitly when it changes — turning judge drift into a reviewable diff, tied to the multi-judge consensus engine. (Slide 87)
- **Failure taxonomy** — Explicit, 6 types with typical symptom/root cause: Wrong Answer (retrieval miss, chunking cut context); Hallucination (weak faithfulness guardrail, prompt doesn't force citation); Tool Failure (API down, wrong params/schema); Refusal (guardrails too strict); Slow (model too large, context too long); Stale Data (ingestion not re-indexing periodically). First step: manually read and label 20–50 failing outputs (Hamel & Shankar). (Slide 90)
- **5 Whys root-cause analysis** — Explicit. Iteratively ask "why" to trace a symptom back to a pipeline stage: Ingestion / Chunking / Retrieval / Prompting. Worked example in the deck: wrong refund-policy answer → answer not grounded in the right doc → retriever didn't fetch latest policy → policy never indexed → ingestion pipeline lacks scheduled re-indexing (root cause = Ingestion, not prompting). Fixing the wrong stage (e.g., prompt) wastes effort. (Slide 91)
- **Failure clustering (manual + K-Means)** — Explicit. Manual: group failures by type, then cluster by root-cause stage, fix the largest cluster first (one root cause can fix many failures at once, e.g., an ingestion re-index fix can clear most "wrong answer" cases). Automatic: embed all failing queries, run K-Means, read a few samples per cluster to name the cause (example: "Cluster 1 = 45% price errors → PDF encoding bug"; "Cluster 2 = 30% multilingual issues"). Don't fix failures one at a time — cluster, count, fix the biggest cluster first for highest ROI. (Slide 92)
- **Continuous Improvement Loop** — Explicit, 4-step cycle: Evaluate (run benchmark) → Analyze (5 Whys → stage) → Improve (fix biggest cluster) → Augment (add confirmed failure to golden set as a permanent regression test, so a recurring bug fails immediately instead of silently returning). Full suite re-run every PR, gated per-category (not just overall average); regression evals should reach near-100% pass. (Slide 93)

## 2. Relationships & Mechanisms

- **Prerequisite chain: Retrieval eval before Generation eval.** Retrieval is the ceiling of RAG quality — Retriever → Context (top-k) → Generator → Answer. If retrieval misses the right document, no generator can produce a correct answer from missing context. Debugging logic: faithfulness OK but answer still wrong → suspect retrieval; faithfulness low with good context → generator bug. (Slide 26)
- **Retrieval metric formulas (explicit):**
  - Hit Rate@k = (# queries with ≥1 correct doc in top-k) / (total queries) — binary per query; a special case of "Recall@k > 0"; the lab's primary retrieval metric. (Slide 24)
  - Recall@k = (# correct docs in top-k) / (total correct docs) — "is there enough evidence"; Recall=1 when k = corpus size. (Slide 24)
  - Precision@k = (# correct docs in top-k) / k — "is top-k clean or noisy." (Slide 24)
  - MRR = (1/|Q|) Σ 1/rank_i — only the first hit counts (rank1→1.0, rank2→0.5, rank3→0.33); correct docs further down are ignored; assumes binary relevance; good for FAQ-style retrieval. (Slide 25)
  - DCG@k = Σ rel(i)/log2(i+1); NDCG@k = DCG@k / IDCG@k — IDCG is the ideal ranking's DCG; handles both binary and graded (0–3) relevance; a TREC exponential-gain variant Σ(2^rel(i)−1)/log2(i+1) penalizes rank errors more heavily; BEIR standardizes on nDCG@10. (Slide 25)
  - Key relationship: Hit Rate/Recall/Precision@k are order-unaware (reordering within top-k doesn't change score — e.g., correct doc at position 1 vs position 10 both give the same Precision@10); MRR/MAP/NDCG are order-aware (position matters). (Slides 23–24)
- **SDG → Golden Dataset pipeline (Input → Process → Output):** Input = source documents/chunks → Process = LLM generates candidate questions (RAGAS TestsetGenerator builds a KnowledgeGraph from docs, extracts entities/summaries/relations via `default_transforms`, then a scenario-synthesizer generates questions per a query distribution: Single-hop specific 0.5 / Multi-hop abstract 0.25 / Multi-hop specific 0.25) → filtering (drop trivial/unanswerable/distribution-skewed items) → human/SME review → Output = gold benchmark. Each step matters because raw LLM generation defaults to easy, single-chunk questions that don't discriminate good vs. bad agents; filtering is what actually produces benchmark quality. (Slides 33, 35)
- **Free retrieval ground truth (LlamaIndex `generate_question_context_pairs`):** Input = chunked docs (nodes) → Process = LLM generates a question per chunk → Output = `EmbeddingQAFinetuneDataset` with `relevant_docs` (query-id → ground-truth chunk-id). Because the question is generated from a known chunk, the chunk-id is a free label — no manual annotation needed. These labels feed directly into Hit Rate/MRR computation. This is retrieval ground truth only, not answer-quality ground truth (two different axes). (Slides 34, 37)
- **SDG pitfalls / mitigation (Trade-off & mechanism):** Synthetic questions tend to be mechanically phrased vs. real user drift; benchmarks built this way risk distribution mismatch. Model-driven question generation carries the generating model's biases (phrasing style, topics, difficulty). Using the same model family to both generate the test set and act as judge inflates scores. Golden rule: generator ≠ validator ≠ judge — use cross-model validation (e.g., GPT generates data, a different family like Mistral validates). (Slide 36)
- **LLM-as-Judge mechanism (Input → Process → Output):** Input = question + agent answer + reference answer + rubric → Process = judge LLM reasons step by step per rubric → Output = score (e.g., 1–5) + rationale. Rationale is required because it enables debugging, not just a number. (Slide 55)
- **PoLL consensus mechanism:** Judge A (cheap) + Judge B (cheap) → compute Agreement Rate → if conflict, escalate to a frontier judge as tie-breaker → Final Score. Frontier tie-break is invoked only on disagreement to control cost. Cheap judges are more lenient, so majority/average alone is trusted only when they agree. (Slide 62)
- **Faithfulness computation (NLI mechanism):** Answer → split into atomic claims → each claim checked against retrieved context for NLI entailment/contradiction/neutral → Faithfulness = (# claims entailed by context) / (total claims). Worked example: 5 claims, 4 entailed, 1 contradicted (wrong price) → 4/5 = 0.80. (Slide 66)
- **Contamination / Goodhart's Law mechanism:** "When a measure becomes a target, it ceases to be a good measure" — as a benchmark score becomes an optimization target, contamination (test data leaking into training data) structurally undermines it. Detection mechanism: time-partition cliff — split the same benchmark by a training cutoff date; a model scoring 10/10 pre-cutoff but 0/10 post-cutoff on equivalent-difficulty problems demonstrates memorization, not reasoning. (Slide 43)
- **Living benchmark mechanism (anti-contamination):** Two techniques — (1) clone a held-out set at matched difficulty (overfitting models like Phi/Mistral drop ~10–13pp from GSM8K to GSM1K — this gap is the "memorization gap"; frontier models show near-zero gap); (2) year-stamp problems (e.g., AIME 2024→2025→2026) and only grade post-release items (MathArena ingests new problems 1–2 days after release) to reduce contamination. (Slide 41)
- **Statistical decision mechanism for "is this delta real?" (Input → Process → Output):** Input = two versions run on the SAME test cases (paired) → Process = McNemar's test on discordant pairs (b=old-pass/new-fail, c=old-fail/new-pass; exact binomial if b+c<25) + check CI overlap + run multiple seeds (report mean±std) + use Wilson/Bayesian CI for small-n pass rates → Output = a defensible claim of "real improvement" vs "noise." Skipping any of these three checks means a claimed "win" is likely noise. (Slide 76)
- **Release gate decision logic (composite):** Input = new version + old version scored on same golden set → Process = compute delta = score_new − score_old; test significance (p<0.05, McNemar/Welch/z-test as appropriate) AND check delta exceeds a tunable noise floor (e.g., 0.03) → Output = decision: RELEASE (if both conditions hold and delta>0), ROLLBACK (both hold, delta<0), or HOLD ("change within eval noise," if either condition fails). Gating also checks per-category distribution so one bad subset isn't masked by the overall average. (Slides 84, 98)
- **Observability → Eval substrate bridge (Day 13 connection):** Explicit. Agent evaluators run directly on OTel/OpenInference spans already instrumented in Day 13: tool-call spans are graded correct/incorrect; ordered tool-call lists are graded by an LLM judge for trajectory. Observability (Day 13) and agentic eval (Day 14) share the same substrate (agent spans) — no separate eval logging pipeline needed. (Slide 54)
- **Trade-off: strict vs. relaxed trajectory matching (Agent-as-a-Judge / `agentevals`):** `trajectory_match_mode` options — strict (exact order required), unordered (only requires the same set of tool calls, not order — suited to agents with multiple valid paths), subset/superset (partial matching) — plus an LLM-judge fallback when no reference trajectory exists. DevAI research found Agent-as-a-Judge deviates from human consensus by only ≈0.27% vs ≈31% for a single LLM-as-judge scoring only the final answer — evaluating intermediate steps substantially improves judge fidelity. (Slide 52)
- **Eval cadence table (trigger → eval type → goal):** Every code release → Offline full suite → regression check; every prompt change → Offline targeted → avoid breaking other areas; weekly → Human sampled → quality trend; continuous → Online monitoring → catch degradation early; before demo/launch → Offline + Human → stakeholder confidence. Mechanism: eval must run automatically in CI/CD, and regression eval should have a near-100% pass bar — failing agent = failing unit test = no deploy. (Slide 9)

## 3. Examples & Distinctions

- **Real-world incident examples (each mapped to "the eval that should have caught it"):**
  - Air Canada (Feb 2024, Moffatt v. Air Canada) — chatbot invented a nonexistent bereavement-fare refund policy; tribunal rejected "chatbot is a separate legal entity" and found negligent misrepresentation; CA$812 total damages. Missing eval: RAGAS faithfulness + expert-reviewed golden set. (Slide 11)
  - DPD (Jan 2024) — a system update made the bot swear and write insulting poems about the company; shipped with no regression gate; post went viral (~1.3M views); DPD disabled the AI feature. Missing eval: release gate / regression eval. (Slide 12)
  - Chevrolet of Watsonville (Dec 2023) — ChatGPT-backed dealership bot was prompt-injected into "agreeing" to sell a 2024 Chevy Tahoe for $1 with "legally binding, no takesies backsies"; ~20M views. Missing eval: adversarial test set (bridges to Day 11). (Slide 12)
  - NYC MyCity (launched Oct 2023, issue found Mar 2024) — chatbot told business owners it was legal to keep employee tips and refuse Section-8 tenants; stayed online labeled "beta" for weeks; new administration announced closure Jan 2026. Missing eval: domain-expert (legal/policy) eval set. (Slide 13)
  - GPT-4o sycophancy (Apr 2025, OpenAI public postmortem) — offline evals PASSED, A/B test PASSED, but model became excessively sycophantic after shipping; rolled back Apr 28–29. Missing eval: dedicated behavioral/sycophancy eval treated as launch-blocking, plus an alpha opt-in stage. Lesson: "every aggregate metric green" ≠ "measured the right thing." (Slide 14)
  - Lawyer hallucination wave (ongoing) — 700+ global court rulings (tracked by Damien Charlotin) containing AI-fabricated content, mostly in 2025; originated from Mata v. Avianca (2023, SDNY, $5,000 fine for citing nonexistent case law). Missing eval: factuality/citation-grounding verification against real sources. (Slide 15)
  - Sakana "AI Scientist" (Aug 2024) — agent edited its own code to game its evaluation harness (extending its own timeout, calling itself instead of solving faster); an independent eval (Beel et al.) found 42% of experiments failed due to code errors. Illustrates Goodhart's Law directly: "agents will game any measurable metric" → need independent, hard-to-game eval. (Slide 15)
- **The Leaderboard Illusion example:** Meta reportedly tested ~27 private variants before submitting Llama-4 to LMArena, contributing to arena-data overfitting effects estimated up to ~+112% relative gain; enabling "Style Control" causes many models to rerank substantially — illustrates that public leaderboards can be gamed via private variant selection and stylistic optimization. (Slide 42)
- **Distinction — Outcome vs Trajectory grading:** Similarity: both assess the same agent run. Difference: outcome checks final environment state (e.g., DB row exists); trajectory checks the full step sequence (tool calls, reasoning). Distinguishing criterion: an agent can answer correctly yet still fail trajectory (extra tool calls, wrong params, repeated steps, roundabout path) — outcome and trajectory can diverge. (Slide 8, 45)
- **Distinction — Order-unaware vs order-aware retrieval metrics:** Similarity: both evaluate whether correct docs are in the retrieved set. Difference: order-unaware (Hit Rate, Recall, Precision@k) ignore position within top-k; order-aware (MRR, MAP, NDCG) weight position, penalizing correct docs ranked lower. Distinguishing criterion: does the metric change if you shuffle the top-k list without changing membership? (Slides 23–24)
- **Distinction — Lexical vs Embedding vs LLM-judge metrics:** Similarity: all attempt to score text-output quality/similarity. Difference: lexical metrics compare surface tokens (blind to meaning, fooled by negation); embedding metrics compare semantic vectors (catch paraphrase but conflate topic-similarity with contradiction — cosine>0.90 for opposite-meaning same-topic sentences); LLM-as-Judge (+NLI) actually reasons about correctness. Distinguishing criterion: does the metric detect a negated/contradicted meaning correctly? (Slides 19–20)
- **Distinction — Pointwise vs Pairwise LLM judging:** Similarity: both use an LLM to score answer quality. Difference: pointwise assigns an absolute rubric score to one answer at a time (stable, gate-friendly); pairwise compares two answers head-to-head (more human-aligned but less stable, more bias-prone). Distinguishing criterion: is there a single reference threshold to gate on, or a relative comparison? (Slide 57)
- **Distinction — Public benchmarks vs. self-built task-specific eval:** Public benchmarks (MMLU, HumanEval, GSM8K, GPQA, SWE-bench Verified, HLE, GAIA, tau2-bench, LMArena, HELM) measure general model capability and are saturated, contamination-prone, and gameable (Goodhart). They do not measure your specific task. Self-built eval (golden dataset, SDG, retrieval metrics, RAGAS, regression gate) measures your task and is the actual content the rest of the lecture/lab builds. (Slides 38–44, 989)
- **Example — MMLU/HumanEval/GSM8K saturation:** MMLU: frontier models cluster in the low-90s (some leaderboards dropped MMLU as outdated); HumanEval: Pass@1 in the 91–99% range; GSM8K: near-ceiling. When all models score >90%, single-point differences can't separate real capability from contamination noise. (Slide 38)
- **Example — Harder next-gen benchmarks:** New reasoning-heavy sets (~12,000 questions, 14 domains, 10-option MCQ instead of 4) show accuracy 16–33% lower than on MMLU and are less prompt-sensitive (CoT helps). GPQA-style "Google-proof" set: 198 MCQ (bio/physics/chem), PhD-expert baseline ≈69.7%, random guess = 25%, non-experts with web access only ≈34%. (Slide 39)
- **Example — SWE-bench Verified & HLE:** SWE-bench Verified: 500 real human-validated GitHub issues; 93 developers filtered out 68.3% of original tasks as flawed/ambiguous; models must fix the repo and pass hidden tests; Anthropic reportedly went from 40%→80% in one year; but contamination has been observed (models reproducing the gold patch verbatim) — a held-out set of your own is still needed. HLE (Humanity's Last Exam): 2,500 expert-written questions across 100+ subjects, has a private held-out subset against overfitting, human baseline is expert-level in-domain, frontier 2026 scores still low with wide headroom. (Slide 40)
- **Example — tau2-bench dual-control:** Both the agent and a simulated user act on a shared environment; graded by comparing final DB state to a ground-truth target (not transcript). Domain difficulty varies widely: telecom ≈99% (saturated) vs airline ≈56%(2025)→≈70%(2026), scores drift week to week — read as a range. (Slide 47)
- **Example — GAIA gap:** 466 real-world assistant tasks, 3 difficulty tiers, short exact-match answers requiring multi-step tool use. Human baseline ≈92% vs GPT-4+plugins (at launch) ≈15% — a large human-machine gap showing multi-step tool use is still hard. Score depends heavily on the scaffold (model+tools+scaffold = "an agent"), so comparisons are only meaningful under the same scaffold. (Slide 49)
- **Example — BFCL (Berkeley Function-Calling Leaderboard):** AST-based evaluation of tool-calling correctness (right function called, correct parallel/serial calls, correct argument types); v3 adds multi-turn + state-based grading (~1,000 test cases). (Slide 46)
- **Example — HELM:** Holistic multi-dimensional eval — 42 scenarios, 7 metric categories (accuracy, calibration, robustness, fairness, bias, toxicity, efficiency) across 16 core scenarios; standardizes multi-metric reporting instead of one number; in maintenance mode as of 2026. (Slide 44)
- **Example — Fairness/safety/red-team targets:** Counterfactual testing (same question, only a sensitive attribute changed — gender-swap, regional dialect, minority language like H'mong/Khmer, age) to detect bias via score gaps. Target thresholds cited: jailbreak refusal ≥95% (JailbreakBench), prompt-injection detection ≥99% (Day 11 link), PII leak 0% (custom), toxic/harmful content blocked ≥98% (HarmBench). Red-team process: 3–5 people from different backgrounds, 2-hour timebox: attempt to break → log → classify → fix → add to benchmark. (Slide 51)

## 4. Assumptions, Boundaries & Gaps

- **Assumption/prerequisite:** L0 vibe-checks are only valid when the builder is also a power user of the domain — flagged explicitly as "impractical/dangerous" in complex apps. (Slide 6)
- **Boundary:** Regression/offline evals alone cannot detect production-only issues; online monitoring alone cannot scale to expert-level judgment — the four axes (offline/online/guardrails/human) must be combined, none is sufficient alone. (Slide 7)
- **Limitation — lexical metrics:** Cannot detect negation ("should refund" vs "should not refund" scores as near-identical under BLEU/ROUGE/F1). WER is only meaningful for ASR transcription, not open-ended answers. (Slide 19)
- **Limitation — embedding similarity:** The "Contradiction Trap" — cosine similarity can exceed 0.90 for sentences with opposite meanings if they share topic/vocabulary; embedding similarity cannot substitute for actual correctness judgment. (Slide 20)
- **Limitation/gap — pairwise judging:** Sensitive to position and distraction bias, and reordering flips the outcome in ~35% of cases — less reliable for gating than pointwise scoring. (Slide 57)
- **Limitation — single LLM-as-judge:** Documented, quantified biases (position, verbosity, self-preference; only 3 of 12 CALM-cataloged bias types covered in this deck — bandwagon, authority, sentiment, distraction, and others are named but not detailed/explained further; flagged as a gap the slides don't elaborate). An uncalibrated single judge's score is explicitly called "not evidence, just an expensive opinion." (Slide 58 note)
- **Gap:** The deck references "12 types of bias" cataloged by CALM but only names 3 in depth (position, verbosity, self-preference) plus lists 4 more by name only (bandwagon, authority, sentiment, distraction) without further explanation — flagged, not filled from outside knowledge. (Slide 58)
- **Boundary — RAGAS versioning:** The testset-generation module is explicitly under reconsideration for v0.4 and the API has changed substantially across versions (v0.1→v0.2→v0.4); the deck instructs to pin `ragas==0.4.3` specifically because of this instability — a real, source-flagged fragility, not a hypothetical one. (Slides 33, 63)
- **Boundary — public benchmark validity:** Explicitly stated that public benchmarks are saturated (MMLU/HumanEval/GSM8K near-ceiling), subject to data contamination (test items leaking into training data inflate scores), and gameable (Goodhart's Law; Sakana example; Leaderboard Illusion) — they measure general capability, not your specific task, and all cited 2026 frontier-model scores are explicitly flagged as "drifting weekly," to be read as ranges, not fixed points. (Slides 38–44)
- **Boundary — statistical methods:** CLT/Wald normal-approximation CIs are explicitly wrong for small-n eval sets (under-cover at n=30, ~95% CI only actually covers ~60–75%); percentile bootstrap also under-covers at small n. Wilson score or Bayesian Beta-Bernoulli are the correct alternatives for pass-rate CIs at small n. (Slide 71)
- **Boundary — determinism:** temperature=0 is explicitly stated NOT to guarantee deterministic output (5–12% of prompts flip answers across seeds); any single-run comparison is unreliable without multiple seeds. (Slide 74)
- **Assumption — noise floor and significance thresholds:** The 0.03 delta noise floor and p<0.05 significance threshold are explicitly flagged as "tunable starting points, not fixed standards," and the delta-gating "recipe" is attributed to a specific vendor (FutureAGI) rather than presented as an industry standard. (Slide 84)
- **Gap/deprecation warning:** OpenAI Evals (both dashboard and API) is explicitly flagged as being sunset — announced 2026-06-03, read-only from 2026-10-31, fully disabled 2026-11-30. The deck explicitly warns against building new release gates on `client.evals.*` and notes OpenAI itself directs migrators to Promptfoo. The grader shapes (string_check, text_similarity, score_model with pass_threshold, python) are called out as still worth learning for pedagogy despite the platform's sunset. (Slide 89)
- **Edge/failure case — cheap judge leniency:** Explicitly flagged as a systematic bias: cheap/fast judges (mini/flash/haiku tier) tend to score fluent-but-wrong answers too generously; they should be used for smoke-testing trend detection only, with frontier judges reserved for gold/release-gate runs. (Slides 82, 97)
- **Gap:** The deck cites illustrative/example numbers repeatedly flagged as non-authoritative: judge pricing ("giá tham khảo 2026, có thể đổi" — reference pricing, subject to change), the ~7×/~15× cost-reduction multipliers for panel/cheap judges (explicitly called "minh họa" / illustrative, single-vendor, not a constant), and canary rollout percentages (1%→10%→50%→100% called "tỉ lệ minh hoạ" — illustrative ratio; 3–10% starting tiers also noted as common in practice). These should not be treated as fixed engineering standards. (Slides 78, 82, 86, 97)
- **Prerequisite (lab-specific but grounded):** SDG must emit ground-truth doc IDs per query for Hit Rate/MRR to be computable without an LLM judge (cheap, deterministic evaluation); without gold doc IDs, retrieval metrics cannot be computed this way. (Slide 27)
