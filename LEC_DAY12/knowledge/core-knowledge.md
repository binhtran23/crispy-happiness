# Core Knowledge

**Source:** `stream (1).pdf` — "Deployment — Đưa Agent Lên Cloud" (AICB-P1, Ngày 12), 84 numbered slides / 104 PDF pages (extra pages are animation-build fragments of the same slides). Page references below (`p.N`) use the deck's own footer slide numbers (`N / 84`).

## 1. Core Concepts

**Environment Parity — Dev ≠ Production** (p.5) — Explicit. Dev (localhost) differs from production across 5 axes: Dependencies (manual `pip install` vs packaged in container), Config (`.env` file vs env vars/secrets manager), Networking (localhost:8000 vs HTTPS/domain/load balancer), Users (1 vs N concurrent), Failure handling (manual restart vs auto-restart/health check). Principle stated explicitly: "Environment parity: dev/staging/prod càng giống nhau càng ít bug khi deploy."

**Three Properties That Break Normal Web Infra** (p.6) — Explicit, the organizing thread of the whole lecture. Agents differ fundamentally from a CRUD app (<1s response) in three ways: (1) **Long-running** — reasoning loop runs 10–60s+ (sometimes minutes), breaking the 29–60s timeout of typical gateways/proxies; (2) **Stateful** — has conversation memory + tool history, conflicting with the "stateless process" rule of 12-factor; (3) **Costly** — every call resends the whole history → cost scales superlinearly (50–1000× tokens vs chat). Every later section of the lecture resolves a consequence of one of these three.

**12-Factor App Applied to Agents** (p.7) — Explicit. 4 most relevant principles: (1) Config in env — never hardcode API keys; (2) Stateless processes — agent doesn't hold state on the instance; (3) Port binding — export service via a port; (4) Dev/prod parity — keep the gap minimal. Explicit clarification: Factor VI (stateless) means "no sticky sessions" — since agents do have memory, the resolution is to **externalize state**, not abandon the principle. Companion deployment checklist items: secrets management, health check endpoint, structured logging, monitoring endpoint, graceful shutdown.

**Agent Deploy vs Traditional Software Deploy — Same Machinery, Redefined Contents** (p.8–9) — Explicit. What stays the same: CI/CD pipeline, build artifacts, immutable image, canary/rolling deploys, IaC (Terraform), load balancer, health check, 12-factor stateless web tier. What gets redefined: **the test** (eval gate on a golden set / LLM-judge, not exact-match unit tests), **the bill** (token/request, unknown until after running, vs CPU/RAM-hour predictable upfront), **the dependency** (external model: rate-limited, can be deprecated, vs libraries you pin and control), **the state** (conversation/memory via checkpointer, not DB rows), **GPU economics** (not CPU/RAM). Mantra: "Cùng cái hộp; cái bên trong và cách quyết định 'đạt' mới là phần khác."

**The Harness — Six Layers Around the Model Call** (p.10) — Explicit. A coding-agent harness (2026 example) wraps the raw model call in 6 layers: (1) Loop + tools (loop, tool schema, retry, turn limits); (2) Isolation (FS + network as independently toggleable OS-level sandboxes — e.g. macOS Seatbelt, Linux bubblewrap+seccomp); (3) Permission policy (allow/ask/deny, enforced outside the model); (4) Repo-scoped config (files versioned with git, clear precedence — e.g. AGENTS.md/CLAUDE.md, nearest wins); (5) Session/state (session ID, resume, stored outside the process); (6) Non-interactive gateway (exit code + JSON + per-run cost). Key point: "Lời gọi model chỉ là một dòng trong sáu. Prompt không phải biên giới bảo mật" — instructions in a prompt/CLAUDE.md do not change what the agent is actually permitted to do at the enforcement layer.

**Model as an Uncontrolled Dependency** (p.11) — Explicit. Unlike a pinned library in `requirements.txt`, a model lives on someone else's server and can be deprecated with a provider-set throughput ceiling. Deploy-time responsibilities: pin model ID + disable auto-upgrade (treat as a deploy artifact); providers typically give ≥60 days' notice before disabling a model (cited concrete example: Assistants API removed 26/8/2026, gpt-4o/4-turbo/3.5 turned off 23/10/2026). Rate limits (RPM/TPM) scale by provider-assigned tier (e.g. GPT-4o tier 1 = 500 RPM → tier 5 = 10k) — this ceiling is set by the vendor, not your autoscaler; mitigation = retry/backoff + multiple keys (see LLM Gateway/Router). Explicit framing: "Lịch khai tử model của nhà cung cấp là một forcing function lên release calendar của bạn."

**Containerization Fundamentals** (p.12–15) — Explicit. A container packages application code + dependencies + runtime config on a minimal OS layer (Debian slim/distroless), producing one unit that runs identically on laptop/cloud VM/Kubernetes ("build once, run anywhere"). 2026 best-practice Dockerfile is **multi-stage + `uv`**: Stage 1 (builder, `python:3.12-slim`) installs deps with `uv sync --locked` (uv is Rust-based, ~10× faster than pip, cache-mountable); Stage 2 (slim runtime) copies only the built `.venv`, sets `USER app` (non-root), target **<500MB**. Base-image trade-off table: `python:3.12` full (~1.0GB, unnecessary attack surface) vs `python:3.12-slim` (~150MB, default for ML Python — glibc/manylinux wheels) vs `distroless` (~66MB, smallest+safest but no shell, hard to debug) vs `python:3.12-alpine` (~55MB, **avoid for ML** — musl libc means packages without musllinux wheels must compile from source; by 2026 numpy/pandas/matplotlib mostly have musllinux wheels but matplotlib still lacks aarch64, so Apple Silicon/Graviton still builds from source — slim remains the recommended default). Image security = 3 mandatory practices: scan for CVEs (Trivy/Docker Scout/Grype) before deploy, run as non-root, pin base image by digest (`FROM ...@sha256:...`) instead of a mutable tag. SBOM (SPDX/CycloneDX, generated via `syft`/`docker buildx --sbom`) lists every package in the image and is now a **legal requirement** (US EO 14028, EU CRA — CRA requires reporting to ENISA within 24h from 11/9/2026, full obligations + SBOM from 11/12/2027). Distroless has fewer CVEs but not zero — scanning is a repeated practice, not a one-time step.

**Docker Compose & Minimal Agent Service** (p.16–17) — Explicit. A typical agent stack = agent service (FastAPI + LLM logic) + vector store (Qdrant, ports 6333/6334) + cache (Redis 6379, for session/rate-limit) + optional reverse proxy (Nginx); services address each other by DNS service name (e.g. `qdrant:6333`). 2026 Compose conventions: `docker compose up` (V2, no hyphen), drop the obsolete `version:` key, use `depends_on: condition: service_healthy`. For the lab: start with 2 services (agent + vector store), add Redis/Nginx only when scaling is actually needed. Minimal FastAPI service pattern: `GET /healthz` returns `{"status": "ok"}` (health check for LB/Cloud Run); `POST /chat` streams via `EventSourceResponse` — **streaming is the default, not the exception** for agent responses.

**The Agent Timeout Problem** (p.18) — Explicit. An agent's reasoning loop is typically longer than infra's default timeout, so requests get cut off mid-stream (user sees a 504). Concrete default timeouts: AWS API Gateway 29s→504 (raisable since 6/2024); Heroku router 30s to first byte (not configurable); AWS ALB idle 60s (cuts stream silently); nginx `proxy_read_timeout` 60s (between reads); Fly.io proxy idle 60s (streaming resets the timer); Railway public HTTP 15 min (private network = unlimited). Two ways past it: (1) stream token-by-token; (2) route through a private network or an async job.

**SSE Streaming — De Facto Standard for LLM Output** (p.19) — Explicit. Server-Sent Events chosen over WebSocket because token streaming is one-directional (server→client) and runs on plain HTTP/1.1; `EventSource` auto-reconnects using `Last-Event-ID`; both OpenAI and Anthropic use SSE (`stream: true`). Two common proxy traps: nginx `proxy_buffering on` (default) batches tokens — disable it or set header `X-Accel-Buffering: no`; if the agent is silent >60s, send a heartbeat ping every ~15s to avoid idle-cut. If a stream breaks mid-way: buffer tokens into Redis keyed by `streamId`, replay on reload from the break point — this only rescues a page reload, not a true resume.

**Async Job Pattern (Submit-and-Poll)** (p.20) — Explicit. When a task would exceed timeout limits, switch models: `Client → POST (submit) → API` returns a `job_id` immediately; work goes to a `Job Queue` (Redis/Celery), a `Worker` (agent loop) processes it; client polls or receives a webhook. Tools: Celery (broker), RQ (Redis), Cloud Tasks (managed). For large non-urgent batches, Batch APIs are ~50% cheaper (OpenAI returns within 24h; Anthropic also 50% cheaper, mostly done within 1 hour).

**Statefulness & Externalizing State** (p.21) — Explicit. 12-factor demands stateless processes for scalability, but agents carry memory — resolved by **externalizing state**, not keeping it on the instance. Where to externalize: conversation/session → Redis/Postgres; LangGraph `PostgresSaver` checkpointer keyed by `thread_id`; the payoff — any instance can serve any request, so scaling is unconstrained. **Durable execution** (2025–26 category) lets multi-step/multi-day agents resume after a crash: Temporal (replay-based), DBOS (MIT, Postgres-backed), Inngest (step memoization), LangSmith Deployment (managed persistence). Explicit warning: "sticky session" is only best-effort — Cloud Run breaks it whenever an instance is killed; externalizing state is what actually holds.

**Concurrency & Cold Start** (p.22) — Explicit. Concurrency: use `async def` so one worker serves many requests while awaiting I/O; the trap is a blocking call inside `async def` stalling the whole event loop; Cloud Run concurrency defaults to 80, max 1000/instance. Cold start: heavy ML deps (loading models/embeddings at startup) slow first-request latency — mitigate with min-instances (Cloud Run) / provisioned concurrency (Lambda) to keep an instance warm, and lazy-load rarely used objects out of the cold path. Stated principle: agents are I/O-bound (waiting on the LLM) → raising concurrency saves instances; keep blocking code in a plain `def`.

**Where Does the Agent Loop Run? — The Location Spectrum** (p.23–25) — Explicit. A deployment axis often overlooked: where do the loop + tools + API key actually execute? Options (location / API key / who pays per token / capability): Server-side (backend, key safe, you pay all, frontier-capable — the **default** for production: client is a thin layer only sending messages); Client (UI-only, still needs a proxy, you pay all, frontier); Local-first/BYOK (user's machine, user's key, user pays, frontier); In-browser model (WebGPU, no key needed, cost≈0, ~1–3B capability); On-device (device NPU/GPU, no key, cost≈0, ~3B); Edge (edge node e.g. Workers AI, key at provider, pay-per-call, ~7B+); Hybrid (on-device escalating to cloud, cost rises with escalation, small→frontier). Critical point: **"client-side" is rarely truly keyless** — bundling `VITE_`/`NEXT_PUBLIC_` env vars ships the key straight into the JS bundle where it can be stolen; even "client-side" frontier agents need a **Backend-for-Frontend (BFF) proxy** that injects the key server-side and never sends it to the browser + rate limiting. Only on-device / in-browser models are truly keyless. On-device examples (2025–26): Apple Foundation Models (~3B, offline, free), Chrome Gemini Nano/Prompt API (no data sent out), MS Phi Silica (NPU, Copilot+ PC), WebLLM/transformers.js (WebGPU). Edge example: Cloudflare Workers AI (200+ cities, pay-per-call, OpenAI-SDK compatible) — trade-off is privacy+offline+$0 cost against ~1–3B capability, battery drain, and first-load cold weight loading. Best hybrid pattern: small on-device model handles routine work, escalates to a larger cloud model when difficult (Apple example: ~3B → Private Cloud Compute); routing criteria are typically unpublished.

**4-Tier Cloud Deployment Model (2026)** (p.26) — Explicit. Tier 0 = Managed agent runtime (AgentCore/Vertex) — no infra management. Tier 1 = Railway/Render/Fly.io — <10 min deploy, MVP/demo. Tier 2 = Cloud Run/ECS Fargate — auto-scale, production. Tier 3 = Kubernetes/self-managed — full control, large scale. Course guidance: start at Tier 1 to understand the deploy flow, migrate to Tier 2/3 when the business needs it, or choose Tier 0 to skip infra management entirely.

**Platform Comparison by the Timeout Axis** (p.27–28) — Explicit. Table (Platform / Max request-runtime / Scale-to-0 / GPU / Agent fit): Railway 15 min public / ∞ private, no scale-to-0, no GPU, OK (route internally); Render ~100 min (unverified — see gap below), free-tier scale-to-0, no GPU, OK; Fly.io 60s idle (streaming resets timer), scale-to-0 yes, GPU yes, OK+streaming; Cloud Run 60 min, scale-to-0 yes (incl. GPU), L4 GPU, "Mạnh" (strong); AWS App Runner ~120s, deprecated (Mar 2026, migrate to ECS Express Mode); ECS Fargate unlimited, no scale-to-0, "Mạnh" (always-on); Modal 24h (default 5 min), scale-to-0 with snapshot, H100/A100, "Mạnh" (GPU); Vercel functions 5 min (Hobby)/800s (Pro GA), scale-to-0, no GPU, "Kém" (poor fit). 2026 updates flagged: Railway dropped its free tier (now $5 trial credit); Cloud Run GPU is GA (6/2025, scale-to-zero, ~5s start). Serverless functions (Vercel/Lambda) are explicitly called out as poorly suited to agents: hard timeout caps (5 min default, up to 1800s beta then 504), 4.5MB body cap, and statelessness losing context between invocations — container-based hosting keeps connections open for long streaming and uses min-instance to avoid cold starts. Explicit correction of an outdated claim: "serverless cold start 5–15s" is stale (Cloud Run GPU starts ~5s, Modal snapshot ~10× faster) — the real problem with serverless for agents is the **timeout cap**, not cold start.

**Beyond Request/Response — 2026 Escape Hatches** (p.30) — Explicit. Some 2026 platforms remove the request/response model entirely for long-running work not going through HTTP: Cloud Run Worker Pools (GA 4/2026) — long-running instances pull from a queue, no request timeout ceiling (the "60 min" column doesn't apply); Vercel Workflows — durable execution that resumes exactly where it left off, surviving deploys/crashes; OpenAI Responses API background mode. Old hard caps still exist elsewhere: AWS Lambda hard cap remains 900s (API Gateway's 29s is tighter and sits in front of it); Lambda response streaming is native only for Node.js, not Python. Framing: "Chọn platform giờ là chọn mode" (choosing a platform is now choosing an execution mode).

**Managed Agent Runtimes (Tier 0)** (p.31) — Explicit. A genuinely new 2025–26 category: deploy an agent without managing a container — runtime, memory, and identity are all managed, billed by consumption. Examples with GA dates: AWS Bedrock AgentCore (Oct 2025, 8h/session, isolated microVM per session); Google Agent Runtime (renamed from Vertex AI Agent Engine, Mar 2025 — Sessions + Memory Bank + Code Execution + Example Store); Azure AI Foundry Agent (May 2025, no-code + hosted, free service layer — pay only for tokens); OpenAI AgentKit (Oct 2025, Agent Builder closes 30/11/2026 → migrate to Agents SDK; ChatKit remains). Common traits: framework-agnostic (LangGraph/CrewAI/ADK...), MCP/A2A support (A2A is now v1.0, governed by the Linux Foundation, 150+ organizations), session isolation.

**Framework vs Managed Runtime — Two Independently Chosen Layers** (p.32) — Explicit. Every major vendor ships two separate layers, chosen independently: Anthropic (Claude Agent SDK / Claude Managed Agents, public beta); OpenAI (Agents SDK / AgentKit, ChatKit=UI surface); Google (ADK, 5 languages, OSS / Agent Runtime); AWS (Strands Agents, Apache-2.0 / Bedrock AgentCore); Microsoft (Agent Framework = AutoGen+Semantic Kernel / Azure AI Foundry Agent Service); LangChain (deepagents, MIT / LangSmith Deployment · Managed Deep Agents). Explicit reasoning: "Framework quyết định code bạn viết; runtime quyết định ai bị đánh thức lúc 3h sáng. Đổi framework = refactor. Đổi runtime = re-deploy." Comparing across the wrong layer is flagged as the most common vendor-documentation reading error.

**Session as Tier 0's Operating Unit** (p.33) — Explicit. At Tier 0, the request is no longer the unit — the **session** is, and it has its own ceiling. AWS AgentCore: max 8h, dies after 15 min idle, each session is its own microVM, destruction = full wipe. Modal Sandbox: default 5 min (must set `timeout=` for up to 24h). Claude Managed Agents: sessions last "hàng giờ" (hours), no published hard cap. To exceed the ceiling: Modal Filesystem Snapshot → restore into a new Sandbox; AgentCore managed session storage persists state across sessions; the general principle still holds — if state lives outside the runtime, any ceiling can be crossed. Explicit cost/correctness trap: idle timeout kills a session (and loses unexternalized state) while an agent waits 20 minutes for human approval.

**Tier 0 Billing — A Third Cost Axis** (p.34) — Explicit. Tier 0 adds a second clock beside tokens: **session wall-clock time**. AWS AgentCore: $0.0895/vCPU-hr + $0.00945/GB-hr, only active compute billed (idle & I/O-wait free); gateway $0.005/1,000 invocations. Claude Managed Agents: standard token price + $0.08/session-hour, only while status=running. Cloudflare: Active CPU pricing — only actual CPU cycles billed, time waiting on the LLM is free. Azure AI Foundry Agent: no separate service fee — pay only for model + backing resources. Key question when choosing Tier 0: **does the clock run while the agent is waiting?** — since agents are idle-heavy workloads (mostly waiting on the LLM).

**Runtime as an Uncontrolled Dependency** (p.35) — Explicit, mirrors the earlier "model as dependency" framing. Evidence from within this very lecture: OpenAI Agent Builder closes 30/11/2026 (13-month lifecycle, exit = Agents SDK); OpenAI Evals closes on the same schedule (→ Promptfoo); AWS App Runner → ECS Express Mode; LangGraph Platform renamed to LangSmith Deployment (renaming itself is a risk — your docs/IaC may still point to the old name). Three questions to ask before choosing a runtime: what do you pin (SDK version, API version, base image)? What's your exit route (can you export state/config)? How long would migration actually take (estimate honestly)?

**Tier 0 vs Self-Deploy Decision** (p.36) — Explicit. Choose Tier 0 when: shipping fast with no infra team, need session isolation + memory out of the box, agent runs very long (AgentCore 8h), already inside AWS/GCP/Azure ecosystem. Choose self-deploy (Tier 1–3) when: need full stack control, avoiding vendor lock-in, optimizing cost at large scale, or compliance/networking requirements. Explicit course decision: Lab 12 self-containerizes and deploys (Tier 1) specifically to learn the mechanism; Tier 0 is a valid production choice when you don't want to manage infra — "biết là đủ" (knowing about it is sufficient for this course).

**Deep Agents — LangChain's 3-Tier Ladder & 4 Infra Decisions** (p.37–39) — Explicit. LangChain frames its product as a ladder (maps ~1:1 onto Tier 0–3): OSS `deepagents` (MIT) — you own all hosting, max control, self-configure persistence; LangSmith Deployment — you own application+server code, for teams needing custom routing/advanced auth/large scale; Managed Deep Agents — you own only agent code/tools/middleware/instructions, LangChain runs backend/store/checkpointer/memory/skills/sandbox/identity (explicitly **private beta**: waitlist, US-region only, CLI-first, "behavior may change," pricing unpublished — "biết là đủ, đừng thiết kế kiến trúc quanh nó"). Deploying Deep Agents requires 4 infra decisions: filesystem backend (StateBackend=default, per-thread, not shared; StoreBackend/CompositeBackend=shared across threads; FilesystemBackend/LocalShellBackend touch the host directly — docs say don't use in a deployed agent); sandbox scope (thread-scoped = fresh sandbox per conversation, cleaned at TTL; assistant-scoped = shared → files/packages accumulate → must set a TTL); secrets via an auth proxy that injects credentials into outgoing requests (so secrets never enter the sandbox). Two additional traps: LangSmith Deployment auto-configures a persistent checkpointer — self-hosting means you must build this yourself (flagged as the largest local→prod delta); shared memory is a prompt-injection vector — namespace it per user (links to Day 11). **"Open source" ≠ free self-hosting**: server license often differs from library license — e.g. LangGraph core library is MIT (free) but `langgraph-api` (server) is Elastic-2.0 (needs a license key + egress to `beacon.langchain.com`, air-gapped mode exists); n8n = Sustainable Use License (internal/non-commercial only); Dify = modified Apache 2.0 (no multi-tenant SaaS, no logo removal); Claude Code = proprietary (not open source at all); Codex CLI/opencode/goose = Apache-2.0/MIT/Apache-2.0 (unrestricted); Crush = FSL-1.1-MIT (source-available but no competing use, MIT after 2 years). Three questions when you see "open source": does the server license match the library license? is there an `ee/` (enterprise edition) folder? does it phone home to validate a license? And OSS status can be revoked later — Daytona closed its sandbox-layer source on 11/6/2026.

**MCP Transports — stdio vs Streamable HTTP** (p.40) — Explicit. stdio (local): client spawns the server as a subprocess, talks via stdin/stdout, runs on the same machine, no OAuth needed (credentials from env), suited to dev/desktop. Streamable HTTP (remote): a single endpoint (e.g. `/mcp`), POST+GET with SSE inside, an independent process serving multiple clients, replaces the old HTTP+SSE transport (2024-11-05), and **must be hosted and secured like a real API**. Per the 2026-07-28 spec, remote MCP servers must use OAuth 2.1; stdio does not need it.

**MCP 2026-07-28 — Protocol Becomes Stateless** (p.41) — Explicit. Spec evolution: 2025-06-18 → 2025-11-25 → 2026-07-28. Biggest change: "Make MCP stateless" — drops the `initialize` handshake and the `Mcp-Session-Id` header; the old HTTP+SSE transport is deprecated (12-month transition). New headers `Mcp-Method`/`Mcp-Name` let a router dispatch without parsing the JSON body. Deployment consequence: any request can land on any instance behind a plain round-robin LB — no sticky session, no session store needed, scale-to-zero is comfortable. This directly reinforces the earlier Statefulness lesson: externalize state → free to scale. Transition caveat: a deployed server must still stay backward-compatible with 2025-era clients during the transition — don't delete the old code path yet.

**OAuth 2.1 for MCP — Three Named Spec Traps** (p.42) — Explicit. Trap 1, Token passthrough: server MUST NOT accept a token not issued specifically for it — the spec explicitly forbids this because it disables rate limiting and audit trails downstream. Trap 2, Confused deputy: a proxy must maintain a per-user registry of approved `client_id`s and check it before every flow — authenticating the right user ≠ authorizing the right client. Trap 3, Discovery has changed: since 2025-11-25 (RFC 9728), `WWW-Authenticate` is now optional, falling back to `.well-known`; the 2026-07-28 spec tightens further — validate `iss` per RFC 9207, declare `application_type` at registration, and DCR (Dynamic Client Registration) is being phased out in favor of CIMD. stdio needs none of this — but the moment a server goes remote it is a public API with full obligations.

**MCP Server Is a Real API — Three CVEs as Proof** (p.43) — Explicit. CVE-2026-33032 (nginx-ui, CVSS 9.8, actively exploited): `/mcp` had `AuthRequired()` but `/mcp_message` did not — 12 tools needed no credential, full server takeover in 2 requests → lesson: authenticate EVERY route, this is a deploy bug, not a protocol bug. CVE-2025-6514 (mcp-remote, CVSS 9.6): command injection in the OAuth proxy itself — merely connecting to a malicious server yields RCE on the client machine → the proxy layer is itself attack surface. CVE-2025-68143/4/5 (Git MCP server, by Anthropic): path traversal + argument injection; `git_init` was removed entirely → even the protocol creator's own reference server has vulnerabilities. Explicit warning: many MCP servers are thin wrappers around a CLI — deploying remotely exposes that CLI to the internet, so container it, run non-root, and use an egress allowlist.

**Deploying MCP — Registry, Gateway, Runtime (3 Layers)** (p.44) — Explicit. Registry (to discover): Official MCP Registry — `server.json` + reverse-DNS namespace; metadata only, NOT hosting; solves discovery, not trust. Gateway (to aggregate & control): Docker MCP Gateway (one isolated container per server, centralized secrets); AWS AgentCore Gateway (aggregates Lambda/REST/MCP behind one governed endpoint). Runtime (to actually run): Cloudflare Workers + OAuth 2.1 via `workers-oauth-provider`, or your own container (per the Docker section). 2026 pattern: registry to find → gateway to aggregate+control → runtime to run — don't let every agent plug directly into 20 separate servers.

**API Gateway Architecture** (p.45) — Explicit. Every request should pass: Auth Check → Rate Limiter → Input validation + Budget check, before reaching agent logic; failures return 401/429 and reject immediately. Principle: "Reject sớm = tiết kiệm tokens và tiền" (rejecting early saves both tokens and money).

**Authentication Patterns** (p.46) — Explicit. API Key (simplest, `X-API-Key` header) — use for internal/MVP/B2B (M2M). JWT Token (stateless auth, bearer token + expiry) — use for user-facing apps/microservices. OAuth 2.1 (delegated auth + PKCE, the standard for remote MCP/agent) — use for platform/remote-MCP scenarios. Guidance: API key is enough for an MVP — don't over-engineer auth before real users exist; but OAuth 2.1 is mandatory by spec if hosting a remote MCP server.

**Cost Protection / Admission Control** (p.47) — Explicit. Real documented risks: $47,000 burned in 11 days from 4 agents retrying infinitely (logs existed but no hard limit); $96,000 Vercel bill (Cara app scaling 100k→900k users in days); prompt injection causing token explosion; leaked API keys used by attackers. Protections: **pre-call admission control** (check remaining budget before calling the LLM, reject if it would exceed); per-tenant budget (keyed by tenant/workload/model); rate limiting (token bucket: rate + burst); circuit breaker (shuts down on anomaly). Critical trap flagged explicitly: a "spend alert" only **notifies**, it does **not block** — a hard cap is a separate feature that must be manually enabled; provider alerts are reactive, so you must still build your own pre-call admission control.

**HTTPS, Secrets & OWASP** (p.48) — Explicit. Security basics: HTTPS auto-issued by Railway/Render; CORS is browser-only control — NOT authorization, the API still needs auth; use a secrets manager (Doppler, Infisical) instead of `.env` for rotation+audit; GitHub push-protection auto-revokes leaked keys by default. OWASP LLM Top 10 (2026) items named: LLM01 Prompt Injection, LLM02 Sensitive Info Disclosure, LLM06 Excessive Agency, LLM10 Unbounded Consumption (cost/DoS) — list not stated as exhaustive here (only 4 of 10 named). Agentic-specific extensions named: ASI03 (Identity), ASI04 (Supply Chain) — full coverage deferred to Day 11. Immediate check advised: is `.env` in `.gitignore`? was a key ever committed? if so, revoke and rotate immediately.

**Data Residency, ZDR & Compliance** (p.49) — Explicit. OpenAI: 11 storage regions at-rest, but only US/EU/UAE process inference in-region; enabled per-project via a domain prefix (`eu.api.openai.com`), +10% surcharge; ZDR (Zero Data Retention) strips content from logs, forces `store=false`, requires pre-approval. Anthropic: Claude Managed Agents do NOT qualify for ZDR or HIPAA BAA because it deliberately stores history, sandbox state, and output server-side; Claude Platform on AWS ≠ Bedrock — infra is Anthropic-operated, and ZDR is obtainable there. Explicit note: Vietnam is not in any listed processing region, so by default data leaves the country; if legal requirements mandate in-country data, the remaining option is self-hosting.

**Hard Spend Caps — Provider Enforcement Compared** (p.50) — Explicit. OpenAI: has a real hard cap but must be manually enabled (Hard Spend Limit at org and project level, returns 429) — the older "spend alert"/monthly-budget field only warns, doesn't block. Anthropic: real hard cap by tier ($500/$1,000/$200,000) — hitting it suspends the API until next month; a workspace spend limit draws from the org's shared quota. AWS Bedrock: **no native hard cap** — must be assembled from Budgets + CloudWatch → Lambda revoking IAM (a reactive circuit breaker, not true admission control). LiteLLM: hard cap by design via virtual-key `max_budget` → 429 `BudgetExceededError`, though a full-bypass issue existed in one release. Conclusion: provider enforcement is inconsistent and not always reliable → **your own admission control is the only layer you fully control**; "hard by design" ≠ "hard in the version you're actually running" — test it yourself.

**Horizontal Scaling by Concurrency, Not CPU** (p.51) — Explicit. Standard load-balancer-to-instances topology, with shared state (DB) behind it. Key point: agents are I/O-bound — one instance can be full of requests waiting on the LLM while CPU stays low. Correct autoscaling signal: concurrency/queue depth (Knative, KEDA on signals like vLLM `num_requests_running`, Ray Serve `target_ongoing_requests`), not CPU. Precondition: the agent must be stateless with state in DB/Redis.

**Health Checks — Three Probe Types** (p.52) — Explicit. Liveness ("still alive?") — fail → restart the container (`GET /health`). Readiness ("ready for requests?") — fail → removed from the load balancer, NOT restarted. Startup — for slow boot (loading weights); gates the other two probes until it passes. Example health endpoint returns: status ("ok"/"degraded"), uptime (seconds), version, dependencies (DB/vector store/LLM reachability). Explicit trap: misconfiguring readiness as liveness causes a useless restart loop.

**Zero-Downtime Deploy & Graceful Shutdown** (p.53) — Explicit. 4-step rollout: start new instance (v2) → health check passes → route traffic to v2 → drain + stop v1 (SIGTERM). Agent-specific point: on SIGTERM, the instance must **drain** in-flight requests since a single agent "turn" can be long — set `terminationGracePeriodSeconds` larger than the worst-case turn length, or requests get cut mid-way. Advanced pattern: Rainbow deployment (Anthropic) — shift traffic gradually to the new version while keeping both running simultaneously, because agents are near-continuously running stateful systems that shouldn't be cut mid-turn; Argo Rollouts adds automated traffic-shift + AnalysisRun-based auto-rollback; Railway/Render support rolling deploys out of the box.

**LLM Gateway / Router** (p.54) — Explicit. A single OpenAI-format endpoint in front of many providers (OpenAI/Anthropic/local-OSS) via LiteLLM (self-hosted, no markup) or OpenRouter (managed, ~5.5% credit top-up fee). Core value: fallback/failover (a failing/rate-limited model auto-switches to a backup group), load-balancing across multiple keys, retry/backoff, centralized cost tracking. Explicit reasoning: a router lets you exceed a single vendor's rate-limit ceiling by using multiple keys/providers, and survive a provider outage.

**Caching to Cut Cost & Latency** (p.55) — Explicit. Prompt caching (provider-side): reuses the KV-cache of a shared prefix (system prompt, RAG context). Anthropic: cache reads ~0.1× cost (~90% cheaper), requires declaring a breakpoint, writes cost 1.25×–2×. OpenAI: automatic for prefixes ≥1024 tokens, reads ~0.1× cost, GPT-5.6+ adds a 1.25× write fee. Semantic cache (your own): returns a previous answer for a semantically similar question (via embedding comparison) — e.g. GPTCache storing query embeddings in Redis — avoiding repeat LLM calls entirely, cutting both cost and latency, but risking a **stale** answer. Distinguishing point: prompt cache matches prefixes byte-for-byte; semantic cache matches by meaning (more powerful, riskier).

**Model Deploy Decision — Call an API or Self-Serve?** (p.56) — Explicit, framed as the "second deploy decision." Four forces toward self-hosting: data residency/compliance (data can't leave a territory/VPC); owning a fine-tune adapter (Bedrock Custom Model Import blurs the line); volume economics (only wins once GPU utilization is high enough — break-even deferred to Day 25; capability ceilings are no longer the blocker per the next slide). Three forces toward staying on hosted API: no spare GPU-hours (hosted bills per token; self-host bills per hour even when idle); capability tiers exist to buy (Fast mode 2×, Scale Tier 99.9% SLA); counter-example — Azure PTU bills per-hour even with no tokens, i.e. exactly what Tier 0 avoids. Explicit framing: three layers, not two — Hosted API → managed self-hosting (you bring weights, they run the serving stack) → fully self-built; the real question is not "which model is smarter" (Day 14) but "do I want to operate one more GPU service."

**Open Models & Serving Engines (If Self-Hosting)** (p.57) — Explicit. Deployable open models (as of 8/2026): gpt-oss-120b (117B total/5.1B active MoE, Apache-2.0, fits one 80GB GPU via MXFP4); gpt-oss-20b (fits in 16GB — commodity hardware tier); Qwen3-235B-A22B (235B/22B, Apache-2.0); DeepSeek-V3.2-Exp (685B, MIT); Kimi K2 (1T/32B, Modified MIT, designed for agentic tool-use). Key MoE fact: VRAM is determined by **active** params, not total. Serving engines by workload shape: vLLM (default across most hardware — NVIDIA/ROCm/Intel/TPU, OpenAI-compatible server); SGLang (best when a prefix is reused often, via RadixAttention — a strong fit for agents); TensorRT-LLM (best on NVIDIA, but requires compiling a dedicated engine); llama.cpp+GGUF (CPU/edge/consumer, 1.5–8 bit quantization). Quantization formats are not interchangeable: GGUF (CPU/edge) ≠ AWQ/GPTQ (GPU) ≠ FP8 (H100/Blackwell). Practical note: ship fine-tunes via multi-LoRA on one base model rather than one GPU per adapter (engine internals deferred to Day 20).

**Self-Hosting = One More Service You Must Deploy** (p.58) — Explicit. Operational changes: cold start is no longer measured in seconds — loading tens of GB of weights takes minutes; readiness probes must wait for weight loading, not just an open port; autoscaling goes by queue depth, not CPU; an idle GPU still costs money (the opposite of Tier 0's idle-free billing). Deploy artifacts gain a **fourth rollback axis**: beyond image/prompt/model-ID (see CI/CD section), self-hosting adds weight (repo+revision), quantization format/engine version — ask explicitly before deploying: "rollback" of *what*? Explicit framing: self-hosting isn't "escaping vendor lock-in," it's trading vendor lock-in for operational work — every item from today (health check, scaling, rollback, cost guard) must be redone for this GPU service.

**Keeping the GPU Busy — Continuous Batching, PagedAttention, Prefix Caching, Speculative Decoding, Disaggregation** (p.59–62) — Explicit, framed as one connecting thread: don't waste KV cache, never let the GPU sit idle, because GPU-hours determine agent serving cost. (1) **Continuous (in-flight) batching**: static batching makes the whole batch wait for the longest request, leaving the GPU idle once short ones finish; continuous batching reschedules the batch every decode step, replacing finished requests immediately — Orca (OSDI'22) introduced iteration-level scheduling, reporting up to 36.9× throughput at equal latency, called "the biggest unlock" for GPU utilization. (2) **PagedAttention** (vLLM, SOSP'23): manages KV cache like an OS manages RAM — fixed-size, non-contiguous blocks instead of contiguous allocation, eliminating near all memory fragmentation → bigger batches in the same VRAM; enables copy-on-write KV sharing across requests (parallel sampling, beam search); vLLM reports 2–4× throughput at equal latency vs prior systems; this is also *why* context length is memory-expensive and why prompt caching (above) saves money — it reuses exactly these KV blocks. (3) **Prefix/prompt caching**: prefill of a shared prefix computed once, reused across requests — put static content (system prompt, few-shot, RAG) at the front of the prompt to exploit this. (4) **Speculative decoding**: a small draft model proposes 5–8 tokens, the target model verifies them in parallel, exploiting otherwise-idle GPU without changing the output distribution — ~2–3× latency reduction; EAGLE-3 reports up to ~4.8× on Llama-3.3-70B. (5) **Disaggregated prefill/decode**: prefill (reading the whole prompt, parallel → compute-bound) and decode (generating one token at a time → memory-bandwidth-bound) have different resource profiles, so they're split into two independently-scaled GPU pools — DistServe (OSDI'24) reports up to 7.4× more requests at the same SLO; Mooncake (Kimi, FAST'25) is KV-cache-centric, serving >100B tokens/day; NVIDIA Dynamo (GTC 3/2025) treats prefill/decode as first-class with a KV-aware router. Practical takeaway: sending the same question twice (cache hit) is cheaper and faster by design — prompt structure should be designed to exploit this.

**CI/CD Pipeline + Eval Gate** (p.63–64) — Explicit. Standard pipeline: checkout → build+push image to GHCR → scan for CVEs (Trivy, fail build on high severity) → **eval gate** (`promptfoo eval --fail-on-error`) → deploy only if evals pass (`railway up`). Eval gate is explicitly called "the AI-specific layer": since agents are non-deterministic, you cannot rely on unit-test exit codes alone — deploy is gated on an eval score ≥ threshold (promptfoo/DeepEval/Braintrust), bridging to Day 14 (Evaluation). Four tools compared, one converged pattern: promptfoo (`--fail-on-error`, or stricter `stats.failures > 0`, PR comment via `promptfoo-action`); DeepEval (`assert_test()`, not `evaluate()` — raises like a normal pytest failure); Langfuse (`experiment-action` on a versioned dataset, PR comment); Braintrust (`eval-action`, blocks merge below threshold, diff view vs baseline branch run). All four converge on comparing against a **baseline-branch run**, not just an absolute threshold — an absolute threshold alone can't catch "dropped 4 points but still above threshold." Side-note flagged: don't pin `temperature=0` — Anthropic is deprecating temperature/top_p/top_k control from Opus 4.7 onward, so any harness pinning `temperature=0` will break with a 400 error.

**Shadow → Canary → Ramp Deployment** (p.65) — Explicit. Shadow (mirror): duplicate traffic to the new version, its output is always discarded, zero user risk. Canary: route a real % of traffic and actually return that output — limits blast radius. Ramp: 10% → 25% → 100%. Auto-rollback is a real primitive: Argo Rollouts' `AnalysisRun` queries Prometheus on a schedule and auto-rolls-back on a failing metric. Agent-specific tax flagged: shadowing runs BOTH versions for every request, **doubling the token bill** — so for agents, shadow a 5–10% sample, not 100%; and shadowing is only safe if the new version's tool calls have side effects blocked — otherwise "no output returned" still deducts real money.

**Rollback Is Not Necessarily One Deploy — Three Independent Artifacts** (p.66) — Explicit. An agent "deploy" actually bundles three independently-versioned things: container image, prompt version, model ID — each has its own rollback path; don't conflate them. Converged pattern across 6 vendors: prompt version is an immutable, content-addressed artifact; a movable label (e.g. `prod`) is repointed to promote or roll back — rolling back a bad prompt/model = moving a label, taking seconds, no deploy, no CI run. Limitation: the label only rescues prompt/config — code and image still go through the full pipeline. Explicit warning: if your prompt lives inside a `.py` file bundled with the image, you don't have fast rollback — you have one long deploy. Separating prompt from code is itself a deploy decision.

**Agent as a CI Job — Minimum Contract** (p.67) — Explicit. Callable contract: exit 0/non-zero for scripts to branch on; `--output-format json` returns `total_cost_usd` per run; "bare" mode disables auto-discovery of hooks/skills/MCP so CI behaves identically on every machine; don't parse the internal transcript — its format is unstable. Who may trigger it, with what rights: gate the triggering identity before the tool-access gate (write access + must be a human); trap flagged — a scheduled trigger has no human actor, so a write-access check can be silently skipped; automation mode defaults to zero tools; OIDC federation should replace a static API-key secret in the repo. An agent CI job has two independent cost axes — compute-minutes and tokens — both must be hard-capped (`--max-turns`, workflow timeout, concurrency limit); and secrets should be phased — granted to a setup script, then removed before the agent loop reads untrusted content.

**Agent "Shapes" — Different Deployment Archetypes** (p.68) — Explicit. Table (shape / trigger / lifecycle / scale / state): Sync chatbot (user request / seconds, timeout / per-request / session store); Cron/background (scheduler / minutes / low, periodic / job state); Batch (dataset/queue / long, async / fan-out / per-item idempotent); Autonomous "run forever" (continuous loop / unbounded / 1 actor per goal / must survive restarts); Embedded copilot (in-app event / seconds / scales with app / app/session); Ambient/event-driven (webhook/event / bursts, long sleep / scale-to-zero / durable across sleep). Explicit key point: state-durability is the main distinguishing axis; "autonomous, runs forever" breaks the request/response model entirely and forces a durable runtime. Multi-agent systems cost ~15× the tokens of a single agent; golden rule stated: "read can be parallel, write cannot" — scale a single agent first, split into multiple only when you hit a real ceiling.

**"Just Retry" Is Dangerous for Agents** (p.69) — Explicit. Ordinary web apps retry on error safely; agents have real side effects (send email, charge a card, book a ticket). Illustrated failure: Agent A calls Agent B to charge a card; the reply is slow; A's timeout fires and it retries → **the card is charged twice**. Root cause: a timeout cannot distinguish "actually failed" from "succeeded but replied slowly," so the caller re-fires the side effect blindly. Stated hard truth: there is no true "exactly-once" for actions that leave the system — only **at-least-once + an idempotent consumer**.

**Idempotency Key — And the Agent-Specific Trap** (p.70) — Explicit. Standard pattern (Stripe): client sends an `Idempotency-Key` (UUID) header with a mutating request; the server stores the first result under that key; a retry with the same key returns the exact same result (even a cached error); Stripe is the de-facto standard, not an RFC (the IETF draft expired). The trap specific to LLM agents: an LLM does not regenerate identical parameters for the same intent → hashing raw content drifts; deduplication must be by **semantic intent** ("same intent," not "same bytes"), and it's unclear who arbitrates whether two actions count as "the same." Practical guidance: every tool call with a side effect should carry a stable idempotency key (e.g. `order_id`), deduplicated server-side via Redis `SET NX` + TTL.

**Durable Execution — Journal the Decision, Don't Re-run the Model** (p.71) — Explicit. If an agent crashes at step 7 (after 4 tool calls), naively restarting from scratch re-pays the LLM and repeats already-logged tool calls. Durable execution's trick: Temporal/Restate/Inngest write the LLM's output to a journal the first time; on replay, they read the journal entry — they do NOT call the model again. Completed steps are memoized and skipped; "the smart part" never reruns. Explicit caveat: **LangGraph is an exception** — its checkpointing happens at the node level, not per individual call, so an unfinished node will re-run its entire LLM call on resume ("checkpoints ≠ durable execution"). Broader caveat: frameworks' "exactly-once" really means "exactly-once on their own datastore" — actions reaching an outside system still need to be idempotent. Provocative framing raised: does a resumed agent still "think," or is it merely replaying the past?

**Saga Pattern & Irreversible Actions** (p.72) — Explicit. Example chain: Hold reservation → Charge card → Send ticket (pivot) → Log. Saga: each step has a compensating (undo) action — there's no automatic rollback, it must be hand-coded. A step that can't be undone (sending an email/ticket) is a **pivot**: place it last and gate it with human approval. Open problem raised, not resolved in the deck: since the agent itself chooses the order of actions, should the runtime forbid it from sequencing an irreversible action before the pivot? Explicit HITL paradox: Temporal can let an agent wait 3 weeks for human approval at zero compute cost — but held reservations/quotes/tokens degrade in the real world regardless; resuming a now-stale decision turns durability into a liability.

**Security: Egress as the Control Point** (p.73) — Explicit, framed as the infrastructure face of safety (distinct from Day 11's behavioral face). A tool calling out = a potential leak channel. The **Lethal Trifecta** (Willison): data leakage needs all three at once — (1) private data, (2) untrusted content, (3) an outbound channel; removing any one blocks the attack. Four 2025 incidents share one mechanism: EchoLeak, CamoLeak, GitLab Duo, AgentFlayer — all rendered an image/HTML to an attacker-controlled URL, and all were fixed by blocking rendering / restricting egress. Explicit caveat: egress allowlisting is the strongest defense, but the leak channel is often a **trusted** one — CamoLeak exfiltrated data through GitHub's own Camo proxy — so you can't allowlist your way out of a provider you already trust.

**Sandbox Spectrum & the "Fail-Open" Lesson** (p.74) — Explicit. Isolation strength gradient (weaker→stronger, with startup time roughly inverse): OS namespace (Docker+seccomp, bubblewrap) → syscall intercept (gVisor, Modal) → microVM (Firecracker, E2B) → V8 isolate (Cloudflare Workers). Concrete cautionary case: CVE-2025-66479 (Claude Code) — setting `allowedDomains: []` (intended as the strictest possible config) actually **failed open** (egress wide open) because the check used `length > 0`; the intended safest state could not be represented. Lesson stated explicitly: default semantics ARE a security property — a system must fail-closed, not fail-open. Correction noted: Cloudflare Sandboxes (GA 13/4/2026) run on Containers, not V8 isolates — V8 isolate isolation applies only to Workers.

**Least-Privilege & Per-Agent Identity** (p.75) — Explicit. Risks: OWASP LLM06 Excessive Agency (too much permission → destructive action); confused deputy (agent tricked into using its own permissions on another's behalf); one shared "god-key" = a single point of collapse. Defenses: each agent gets its own scoped identity; short-lived, per-task tokens; audience-bound tokens (MCP OAuth 2.1); example: Microsoft Entra Agent ID. Explicit stat cited: ~91% of organizations run agents in production, but only ~10% manage them as a distinct identity — per-agent identity at scale is called an unsolved operational problem.

**Agent Identity Standards — SPIFFE & Agent Identity** (p.76) — Explicit. A plain service account is insufficient — agents are ephemeral, have a large blast radius, and a shared key isn't traceable. SPIFFE (CNCF): short-lived X.509 SVIDs with attestation. Google Agent Identity (4/2026): a first-class principal separate from both human and service accounts, with rotating certs, 24h validity. An agent must authenticate in **4 directions**: to a cloud service (bound token tied to a cert); to an external tool/MCP (API key/OAuth); to a user's resources (3-legged OAuth); to another agent (mTLS + DPoP). Explicit limitation: plain OAuth 2.1 cannot express "which agent is acting on behalf of which user" — this is called a draft-stage problem, echoing the earlier idempotency-key lesson that mechanisms here should be designed to be swappable.

**Production Readiness / Deployment Checklist** (p.77) — Explicit, a consolidation slide gathering all prior items: Container (multi-stage+uv, <500MB, non-root; `.dockerignore` + CVE scan; public URL+HTTPS; env vars not hardcoded secrets; SSE streaming; state externalized to Redis/Postgres) and Security/Cost/Reliability (auth — API key/JWT; rate limit + spending cap via admission control; per-project/per-tenant budget; `/health` liveness+readiness; graceful shutdown/drain; rollback plan <2 minutes; pin model ID + disable auto-upgrade; router/fallback for provider failure).

## 3. Examples & Distinctions

**Cost runaway examples** (p.47): $47,000 burned in 11 days by 4 agents retrying infinitely (had logging but no hard limit); $96,000 Vercel bill from the Cara app scaling 100k→900k users in days. Both used to motivate pre-call admission control as necessary since provider "spend alerts" only notify, never block.

**Timeout table across infra layers** (p.18): AWS API Gateway 29s→504; Heroku router 30s to first byte; AWS ALB idle 60s; nginx `proxy_read_timeout` 60s; Fly.io proxy idle 60s; Railway public HTTP 15 min (private network unlimited) — used to justify why agents systematically hit 504s unless streaming or private-networked.

**Platform comparison table by timeout/scale/GPU/fit** (p.27): Railway, Render, Fly.io, Cloud Run, AWS App Runner (deprecated), ECS Fargate, Modal, Vercel functions — full attribute comparison used to argue "the most important axis for agents is request timeout, not price."

**Three named CVEs proving "MCP server = real API"** (p.43): CVE-2026-33032 (nginx-ui, route-level auth bypass, CVSS 9.8); CVE-2025-6514 (mcp-remote, OAuth-proxy command injection, CVSS 9.6); CVE-2025-68143/4/5 (Anthropic's own reference Git MCP server, path traversal + argument injection).

**Four 2025 incidents, one mechanism** (p.73): EchoLeak, CamoLeak, GitLab Duo, AgentFlayer — all exfiltrated data by rendering an image/HTML to an attacker URL; all fixed by blocking rendering or restricting egress; used to illustrate the Lethal Trifecta.

**Fail-open case study** (p.74): CVE-2025-66479 in Claude Code — `allowedDomains: []` (intended strictest) became fully open egress due to a `length > 0` check bug.

**Deploy artifact example command set** (p.79): `gcloud run deploy` (Cloud Run, `--concurrency 8`, `--set-secrets` for API key) vs `railway up` + `railway variables --set` — concrete illustration of "secrets injected via platform mechanism, never baked into the image," and "keep concurrency low per agent instance since each request holds a long streaming connection."

**Cost-guard code example** (p.80): `guard()` function counts input tokens, estimates cost using `IN_PRICE`/`OUT_PRICE` and a `MAX_OUT` assumption, raises `BudgetExceeded` if estimated cost exceeds `MAX_USD_PER_REQ` — concrete implementation of pre-call admission control introduced abstractly on p.47/50.

**Distinguishing pairs:**
- **stdio vs Streamable HTTP (MCP transport)** (p.40) — similarity: both let an agent call MCP tools. Difference: stdio is local-subprocess, no OAuth, dev/desktop use; Streamable HTTP is a remote, multi-client, POST/GET+SSE endpoint that must be hosted and secured (OAuth 2.1 mandatory) like a public API.
- **Liveness vs Readiness vs Startup probes** (p.52) — similarity: all are health-check mechanisms feeding orchestration decisions. Difference: liveness failure → restart; readiness failure → removed from LB (no restart); startup gates the other two during slow boot. Distinguishing criterion: does failure trigger a restart, or just a traffic pause?
- **API Key vs JWT vs OAuth 2.1 (authentication)** (p.46) — similarity: all authenticate a caller. Difference: API key = simplest, static, internal/MVP/M2M; JWT = stateless, expiring, user-facing apps/microservices; OAuth 2.1 = delegated + PKCE, mandatory for remote MCP/platform contexts. Distinguishing criterion: is it delegated auth with an authorization flow, or a static/self-contained credential?
- **Prompt caching vs Semantic caching** (p.55) — similarity: both cut cost/latency by avoiding recomputation. Difference: prompt caching matches an exact byte-level prefix (provider-managed, ~90% cheaper reads); semantic caching matches by meaning via embeddings (self-managed, e.g. GPTCache+Redis) and risks returning a stale/outdated answer. Distinguishing criterion: exact-prefix match vs meaning-similarity match.
- **Static batching vs Continuous (in-flight) batching** (p.59) — similarity: both batch multiple requests on one GPU. Difference: static batching waits for the whole batch's longest request (leaves GPU idle on shorter ones); continuous batching reschedules per decode step, swapping in new requests as others finish (Orca: up to 36.9× throughput). Distinguishing criterion: is the batch composition fixed for its whole lifetime, or re-evaluated every step?
- **Shadow vs Canary deployment** (p.65) — similarity: both are pre-100%-rollout risk-reduction stages. Difference: shadow mirrors traffic and always discards the output (zero user risk, but doubles token cost and requires blocking new-version side effects); canary routes a real % of traffic with real output returned (bounded user risk, single token cost per request). Distinguishing criterion: is the new version's output ever actually shown to a user?
- **Framework vs Managed Runtime** (p.32) — similarity: both are vendor-provided layers for building/running agents. Difference: framework = the library you write agent code with (changing it = refactor); runtime = the managed service that executes/hosts it (changing it = re-deploy). Distinguishing criterion: does this layer determine the code you write, or who operates the 3am pager?
- **Tier 0 (managed runtime) vs Tier 1–3 (self-deploy)** (p.36) — similarity: both are valid production paths for shipping an agent. Difference: Tier 0 trades control for speed/managed session+memory+identity; Tier 1–3 trade convenience for full stack control, lock-in avoidance, and cost optimization at scale. Distinguishing criterion: do you have (or want) an infra team, and do you need vendor-neutral portability?
- **"Just retry" (naive) vs Idempotency-key retry (safe)** (p.69–70) — similarity: both are responses to a failed/uncertain call. Difference: naive retry blindly re-fires a side effect because timeout can't distinguish failure from slow success (double-charge example); idempotency-key retry lets the server recognize "this is the same request" and return the cached result instead of repeating the side effect. Distinguishing criterion: does the retried call carry a stable key the receiver can deduplicate on?
- **Durable-execution "journal+replay" vs LangGraph checkpointing** (p.71) — similarity: both aim to survive a crash without losing all progress. Difference: journal+replay (Temporal/Restate/Inngest) records LLM output at the call level, so replay never re-calls the model; LangGraph checkpoints at the node level, so an unfinished node re-runs its entire LLM call on resume. Distinguishing criterion: is the durability granularity per-call or per-node? Explicit label: "Checkpoints ≠ durable execution."
- **"Open source library" vs "open source server"** (p.39) — similarity: both are labeled open source by the vendor. Difference: the library (e.g. LangGraph core, MIT) may be unrestricted while the server around it (e.g. `langgraph-api`, Elastic-2.0) requires a license key and phone-home — the license boundary sits between components, not at the project name. Distinguishing criterion: check the license file of the specific component you're deploying, not the project's headline license.
