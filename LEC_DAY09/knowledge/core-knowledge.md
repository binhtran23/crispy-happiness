Slide numbering below refers to the deck's own footer counter (p.N / 64); the PDF has 79 physical pages because several slides are built progressively across multiple physical pages (animations) that share the same footer number.

## 1. Core Concepts

- **Single-agent limits (4 core limits)** (p.7): (1) Context bottleneck — one agent must hold goals, tool outputs, evidence, and state in one reasoning pass; context window is a hard limit. (2) Specialization trade-off — the more roles an agent takes on, the longer/less stable its prompt; being "good at everything" tends to mean not truly good at any one role. (3) Limited parallelism — a single agent usually runs sequentially, so independent sub-tasks still wait on each other, adding unnecessary latency. (4) Weak reliability — if the agent picks the wrong tool or misreads the task early, the whole system can drift, with no isolation to contain the error.
- **Context window bottleneck in practice** (p.8): explicit worked scenario — 80-page contract analysis + law lookup + risk summary; a single tool call returns 12,000 tokens, chat history takes 6,000, base prompt 3,000, leaving ≈3,000 tokens for reasoning. Named symptoms: answers missing mid-document info, agent repeating completed steps, unusually short reasoning at the final step, tool calls with empty context. Named as the "lost-in-the-middle" problem.
- **When to consider multi-agent** (p.9, explicit checklist): task has multiple distinct-role steps (plan/retrieve/tool-use/synthesize); work can be split independently (parallel workers make sense); need to debug clearly who is at fault (routing/retrieval/synthesis); need to scale by adding a worker without rewriting the whole base prompt; single agent's context window is insufficient. Explicit caution: don't use multi-agent just because it looks sophisticated — if a simple workflow suffices, keep it simple (cheaper, more stable).
- **System-thinking mental model** (p.10): reframes "how do I make the agent smarter / add more tools to one agent" (old thinking, leads to a "god agent" nobody understands) into "how many types of responsibility does this task have / who needs to know what, when / where should errors be contained / where does this need human oversight" (system thinking → clear roles, testable in parts, improvable incrementally).
- **Three design questions before writing code** (p.11): (1) Where to split responsibility — which tasks need reasoning vs. data fetching vs. just formatting? (2) Which path does information travel — who needs to know what, whose output is needed by whom first? (3) Where is the least-harmful place for errors to occur — design so a worker failure doesn't break the whole system. Good design gives errors a clear "address" instead of letting them propagate.
- **4 Multi-agent patterns** (p.12–16): Supervisor-worker, Pipeline, Debate, Hierarchical (see §3 for the comparison table and distinguishing traits).
- **Supervisor-Worker architecture** (p.17): User Request → Supervisor → {Retrieval Worker, Tool Worker, Synthesis Worker} → Final Answer + Trace.
- **Supervisor responsibilities** (p.18): analyze the initial request; decide which worker(s) should participate; track status and retry if needed; synthesize the final output; know when human review is needed.
- **Worker responsibilities** (p.18): handle one narrow capability; take clear input, return clear output; should be as stateless as possible for testability; local failure shouldn't break the whole architecture; can be swapped without affecting the supervisor. Core principle: "supervisor holds decision flow; worker holds domain skill" — a worker shouldn't secretly also coordinate the whole system.
- **3 traits of good worker design** (p.19): one primary capability (retrieve / call tool / summarize / check policy...); ideally needs only current input rather than the whole system history; has clear input/output contracts so it can be tested independently before wiring into the supervisor.
- **Anti-patterns** (p.20, explicit): "God Supervisor" (supervisor does too much — plan, retrieve, synthesize, monitor — becoming a renamed single agent); "Implicit State" (state passed via global variables/side effects — nobody knows what step the system is on); "Chatty Workers" (workers repeatedly call back to the supervisor for more info, increasing message overhead); "No Fallback" (a worker fails and returns nothing; supervisor waits forever for output to synthesize).
- **Shared state vs. Message passing** (p.21): two coordination approaches — see §3 for comparison. Day 9 simplification: shared state helps coordination; message contract helps unambiguous communication.
- **Minimal state schema for Day 9** (p.22, explicit fields): `task` (original user task), `plan` (list of workers to call), `worker_results` (dict of each worker's output), `status` (pending | running | done | error), `final_answer` (final synthesis), `trace` (timestamped log list). Trace is called out as a mandatory field — without it, nobody can tell after a run which path the agent took to reach its result.
- **MCP (Model Context Protocol)** (p.24–30): a standard protocol for an agent to connect to external capabilities (tools, resources, prompts) without custom-building an adapter per tool/framework. Practical framing (p.25): MCP is a "standard socket" for an agent to use external resources — analogized to USB (every device uses the same connection standard). Agents can list, describe, and invoke capabilities via this shared standard.
- **MCP architecture** (p.26): Agent/MCP Client ↔ (JSON-RPC / HTTP) ↔ MCP Server, which exposes Tools, Resources, and Prompts. The agent doesn't need to know the backend system's details — only the MCP surface the server publishes.
- **What an MCP server can expose** (p.27): actions/operations (e.g., search, query API, create ticket, call webhook); readable resources (e.g., file, schema, catalog, config, DB); reusable prompts (standardize how a capability is invoked, reducing prompt error). Explicit note: not every MCP server needs all three — what matters is the agent has a consistent view of published capabilities.
- **MCP tool discovery flow** (p.28) — see §2 (Relationships & Mechanisms) for the step sequence.
- **A2A (Agent-to-Agent communication)** (p.31–36): a way for agents to hand off/coordinate work with each other, distinct from MCP (agent-to-tool). Goal: task division and synchronization; focus: clear message contract; the receiving agent can make decisions (has agency), unlike a tool.
- **Message contract (A2A)** (p.32–34): structured hand-off with `task` (what the other agent needs to do), `context` (what the worker needs to know to do it correctly — query, constraints, user role, state), `expected_output` (format to return). Worked example (p.33): task = "retrieve evidence"; context = "user asks about refund policy, prioritize documents after 2025"; expected_output = "top 3 chunks + source + confidence". "Need to know" principle (p.34): a worker should receive only the context it actually needs — not more, not less; when unsure, start with less and add as needed.
- **Sync vs. Async (A2A)** (p.35): see §3 for comparison; Day 9 starts with sync, async introduced only as an extension direction.
- **Security & boundaries in agent communication** (p.36, explicit checklist): know who is allowed to call whom (not every agent should touch every capability); know what data is transmitted (avoid pushing excess PII or sensitive state); know which outputs need re-validation (especially when a worker touches an external tool); validate output before use (a worker may return a malformed schema). Explicit caution: don't assume every agent is equally trustworthy — multi-agent systems still need trust boundaries.
- **LangGraph** (p.37–43): an orchestration framework that turns a multi-agent system into an explicit graph of nodes, edges, and state, instead of routing logic buried in one giant orchestration prompt. Supports persistence (state can be saved and resumed) and human-in-the-loop at any point. Condensed mental model (p.38): "node = who does the work, edge = where it goes next, state = what the system currently knows."
- **LangGraph Node** (p.39): a Python function that takes state and returns new state; corresponds to one agent or processing step; can be supervisor, worker, or human review.
- **LangGraph State** (p.39): a TypedDict or Pydantic model passed through every node; each node can read the whole state and write to its permitted fields; described as the "memory" of the whole graph.
- **LangGraph Edge** (p.39): Unconditional edge (always goes from A to B) vs. Conditional edge (a function returns the name of the next node based on state).
- **Human-in-the-loop** (p.43): insert when task risk is high (finance, medical, legal), confidence score is below a threshold, a tool action has an irreversible side effect, output goes to a user/stakeholder, or the system is unsure of original intent. Implementation in LangGraph: add a "human_review" node that interrupts the graph and waits for input; state is preserved across the interrupt; after human approval, execution continues; the human's decision is logged in the trace. Explicit framing: multi-agent ≠ full autonomy — the best systems know when to stop and let a human decide.
- **Observability / trace log** (p.44–48): multi-agent systems are harder to debug than single-agent because error sources are ambiguous (routing, context, tool failure, synthesis) and an error at step A may only surface at step C; more agents = more LLM calls = more potential failure points. 3 observability questions (p.44): which agent ran, in what order? what was input/output at each step? what errors/warnings occurred?
- **Good trace entry design** (p.45, explicit fields): `timestamp`, `agent_id`, `action` (route/call/synthesize/error), `input_summary` (summarized, not full context), `output_summary`, `status` (ok/warn/error), `latency_ms`. Worked JSON example given on p.45.
- **What trace should record** (p.46): what task the supervisor received and by what routing criteria; which worker was called and with what input; what output/confidence/status the worker returned; how the supervisor synthesized the final answer; where retries/timeouts/fallbacks occurred; what a human decided, if human review occurred. Explicit caution: a log that only says "agent finished" teaches nothing about orchestration — good trace must expose the path of decisions.
- **Trace → system improvement loop** (p.47): Run system → Read trace → Find error pattern → Fix (prompt/route/schema) → Re-eval → next cycle. Trace is framed as ongoing improvement data, not just today's debugging tool.
- **Observability tooling landscape** (p.48, explicit but unnamed): three categories described by characteristic rather than named tool — (a) built-in with LangChain/LangGraph, automatic trace, visual flow, run comparison; (b) JSON logs + structured output, described as simplest for Day 9, easy to read/inspect; (c) an open standard for distributed tracing, suited to larger systems needing a dashboard. Note: the source slide itself does not print explicit product names for these three columns (only descriptive text was present — verified via page-image fallback since text extraction returned no header labels). Recommendation: start with self-written JSON logs into state — described as the way to learn the most about how the system behaves.
- **Cost, Latency & Reliability trade-offs** (p.49–51): more agents = more LLM calls = more cost and more failure points. Cost drivers (p.49): each agent = at least 1 LLM call; supervisor is usually a separate LLM call; context passed through state can be large; retry = doubles cost at that point; human review increases latency but not LLM cost. Optimization principle: supervisor doesn't need to be the largest model — if routing logic is simple, use a smaller model for the supervisor and reserve the stronger model for workers needing deep reasoning.
- **Reliability design for worker failure** (p.51): worker needs a clear timeout; supervisor needs retry logic (how many attempts?); if retry also fails, what is the fallback?; local failure shouldn't crash the whole system; partial failure should synthesize results from workers that did succeed. "Graceful degradation" principle: the system doesn't need to succeed at everything — it needs to fail in a controlled, clearly-reported way when not confident enough.

## 2. Relationships & Mechanisms

- **Day 08 → Day 09 progression** (p.5, 23): Day 08 built retrieve/rerank/generate (grounded RAG answering). Day 09 does not negate Day 08 — it's the next step: turning a single RAG agent into a system with roles, coordination, and clear extension points. Concretely (p.23): Day08 RAG Agent —(split roles)→ Day09 Supervisor + {Retrieval Worker, Tool Worker, Synthesis Worker}.
- **Pattern-selection mechanism** (p.13, explicit table) — `Input → Process → Output` framed as "problem type → pattern": Supervisor-worker when task needs routing to the right role (strength: easy control/trace; risk: supervisor can become a bottleneck if overloaded); Pipeline when steps are nearly fixed (strength: easy to understand/test per step; risk: inflexible when flow changes dynamically); Debate when the same problem needs multiple viewpoints (strength: reduces blind spots, increases critique; risk: costly and hard to synthesize); Hierarchical when there are many task groups/management tiers (strength: scales well at large scope; risk: complex to design/debug).
- **MCP tool discovery flow** (p.28, `Input → Process → Output`): (1) agent connects to MCP server → (2) calls `tools/list` to get the tool list → (3) each tool returns `name`, `description`, `inputSchema` → (4) agent reads the schema and decides which tool fits → (5) calls `tools/call` with correct parameters → (6) MCP server executes and returns the result. Why it matters: the agent doesn't need to be hard-coded to know tool "X" exists — it can discover capabilities at runtime and adapt to whatever tools are available.
- **MCP-worker layering** (p.30): MCP sits as a middle layer between each worker and the real capability (e.g., Retrieval Worker↔MCP:VectorDB, Tool Worker↔MCP:API, Synthesis Worker↔MCP:Formatter) — a worker only needs to know the MCP surface, not what's behind it.
- **MCP vs. A2A relationship** (p.31): "same 'calling out', but MCP answers where the agent gets capability from, while A2A answers who the agent hands work to." MCP = tool integration (no agency on the tool side, only execution); A2A = agent delegation (the other side can make decisions).
- **A2A contract failure mode chain** (p.32, explicit): no contract → supervisor calls worker with a vague instruction ("find relevant policy") → worker doesn't know the context → worker returns 10 unfiltered results → supervisor doesn't know which results are usable → the resulting error surfaces at synthesis even though it originated at the call step. With a clear contract, supervisor provides task + context + expected_format up front, avoiding this chain.
- **A2A context sizing trade-off** (p.34): too little context → worker retrieves unsuitable results, requires repeated calls, hard to debug. Too much context → wastes tokens unnecessarily, slows worker processing, harder to maintain as schema changes. Resolved by the "need to know" principle (start with less, add as needed).
- **Trace-to-improvement mechanism** (p.47, `Input → Process → Output`): running the system produces a trace; reading the trace surfaces error patterns; those patterns drive fixes (prompt / route / schema); fixes are re-evaluated, closing the loop into the next run.
- **Sync/Async as a mechanism trade-off** (p.35): Sync — simple to understand/debug, fits when the supervisor needs the result immediately for the next step, but easily raises overall latency; Day 9's starting point. Async — fits when multiple workers run in parallel, exploits concurrency, but requires better state/timeout management; introduced as an extension once sync is understood.
- **Shared state vs. message passing mechanism** (p.21): Shared state gives full visibility, is convenient for graph orchestration (LangGraph), but risks agents "stepping on" each other's writes without discipline, and needs a clear schema (who reads/writes what). Message passing gives a clearer contract between agents and less coupling, but requires careful message-format design and validation at every receiving point.
- **Cost vs. capability trade-off mechanism** (p.49): the supervisor's model size should scale with routing complexity, not be maximal by default — reserve the strongest model for workers doing deep reasoning.

## 3. Examples & Distinctions

- **4-pattern comparison** (p.13, explicit table):
  - Supervisor-worker: use when task needs routing to the correct role. Strength: easy control, easy trace. Warning: supervisor can become a bottleneck if overloaded.
  - Pipeline: use when steps are nearly fixed. Strength: easy to understand, easy to test step-by-step. Warning: inflexible when the flow needs to change dynamically.
  - Debate: use when the problem needs multiple viewpoints. Strength: reduces blind spots, increases critique. Warning: costly and hard to synthesize.
  - Hierarchical: use when there are many task groups and management tiers. Strength: scales well at large/enterprise scope. Warning: complex to design and debug.
- **Pipeline pattern example diagram** (p.14): Input → Parser Agent → Research Agent → Writer Agent → Review Agent. Best fit: flow nearly fixed, each step needs the previous step's output, easy to test each agent separately. Limits: latency accumulates at each step, hard to handle branching flows, retrying one step affects the whole chain.
- **Debate pattern example diagram** (p.15): Task → {Agent A, Agent B, Agent C} → Aggregator. Used when the problem has multiple valid viewpoints, when the risk of being wrong is high, or when cross-checking is needed before an important decision.
- **Why Day 9 chooses Supervisor-Worker as the teaching pattern** (p.16, explicit): pedagogical reasons — learners can see roles easily, easy to connect to real use cases, easy to explain routing logic, easy upgrade path from the Day 08 artifact. Implementation reasons — starting with 2–3 workers is enough, easy to plug in an MCP tool worker, clearer trace/testing, supervisor usually needs only a small LLM call.
- **MCP vs. A2A** (p.31): Similarity — both are ways an agent "calls out" beyond itself. Difference — MCP: agent talks to a tool/capability (goal: connect external capability; focus: a standard surface; the tool has no agency, only executes). A2A: agent talks to another agent (goal: divide work and synchronize; focus: a clear message contract; the other agent can make decisions). Distinguishing criterion: does the other side have agency/can it decide, or does it only execute?
- **Sync vs. Async (A2A)** (p.35): Similarity — both are ways workers/supervisor exchange results. Difference — sync is simpler to debug but raises latency when serial; async fits parallel workers and concurrency but needs state/timeout management. Distinguishing criterion: does the supervisor need the result immediately to proceed, or can multiple workers run independently?
- **Shared state vs. message passing** (p.21): Similarity — both are coordination mechanisms carrying information between agents. Difference — shared state gives full visibility and fits graph orchestration but risks undisciplined overwrites; message passing gives a clearer, less-coupled contract but needs careful format design and per-point validation. Distinguishing criterion: does the mechanism expose a common visible state object, or discrete validated messages between specific senders/receivers?
- **MCP customer-support worked example** (p.29, explicit): Tool Worker needs the latest policy → calls MCP server "knowledge-base" → server exposes tools `search_policy`, `get_faq` → worker calls `search_policy(query, date_after)` → result returns as standard JSON with source. Direct benefits: policy team updates only the MCP server (no supervisor/worker code changes needed when the tool changes); adding a new tool = adding an endpoint to the MCP server; easy to audit who called what tool and when.
- **Single vs. Multi-Agent comparison** (p.50, explicit table): LLM cost (single: lower, 1 call vs. multi: higher, many calls); Latency (single: low if prompt is short vs. multi: can be parallel, but increases if serial); Debuggability (single: harder, hidden logic vs. multi: better, has clear trace); Specialization (single: limited vs. multi: better, each worker is specialized); Scalability (single: hard to scale roles vs. multi: easy to add a new worker); Complexity (single: simpler vs. multi: more complex to set up).
- **Anti-patterns as negative examples** (p.20): God Supervisor, Implicit State, Chatty Workers, No Fallback — see §1 for definitions; these are explicitly flagged as common design mistakes to avoid, distinguishing "good" supervisor-worker design from a mis-implemented one.
- **A2A message contract worked example** (p.33): task = "retrieve evidence"; context = "user asks about refund policy, prioritize documents after 2025"; expected_output = "top 3 chunks + source + confidence" — used to illustrate what "task / context / expected_output" concretely look like.
- **Common misconceptions vs. reality** (p.55, explicit table): "More agents = a better system" → Reality: more agents = more complexity, use only when needed. "Supervisor must be the largest model" → Reality: supervisor only needs to be good enough to route correctly. "MCP and A2A are the same thing" → Reality: MCP = tool integration; A2A = agent delegation. "Multi-agent automatically solves the context problem" → Reality: context still must be managed carefully. "LangGraph can only be used with LangChain" → Reality: LangGraph works with multiple LLM frameworks.

## 4. Assumptions, Boundaries & Gaps

- **Prerequisites (explicit, p.53)**: From Day 08 (required) — working RAG pipeline (query → retrieve → generate), basic tool calling, ability to write a structured system prompt, and a working Day 08 artifact. Python foundations (needed) — TypedDict and type hints, dictionary operations, basic function decorators, async/await if going into async A2A. Explicit note: learners without a working Day 08 artifact should spend the first 30 minutes fixing it before starting the Day 09 lab.
- **Boundary: when NOT to use multi-agent** (p.9, explicit): if a single simple workflow is already sufficient, keep it simple — cheaper and more stable. This is an explicit constraint on applying the whole lecture's content.
- **A2A context-sizing constraint** (p.34): "need to know" principle — worker should receive only the context it needs, no more/no less; when uncertain, start with less. This is presented as a design discipline, not an algorithm — no formula given for determining "enough" context.
- **Security/trust boundary checklist** (p.36) is presented as a checklist of what to know (who may call whom, what data is transmitted, which outputs need re-validation, validate before use) but the slides do not specify *how* to implement enforcement (e.g., no auth mechanism, no policy engine described) — flagged as a gap; mentioned at a principle level only.
- **Human-in-the-loop thresholds are unspecified** (p.43): triggers listed (high-risk task, confidence score below a threshold, irreversible tool side-effects, output to user/stakeholder, unclear intent) but no concrete threshold values or scoring method are given — flagged as a gap for the source to fill or lecturer to specify.
- **MCP protocol depth intentionally limited** (p.24, explicit): the slide states the learning goal is understanding *why* MCP helps scale a system, not memorizing the protocol spec in the first session — so deeper MCP protocol details (e.g., full JSON-RPC message formats) are out of scope for this lecture and not present in the source.
- **MCP transport mentioned but not explained** (p.26): "JSON-RPC / HTTP" appears on the architecture diagram as the connection between Agent/MCP Client and MCP Server, but no further explanation of the protocol mechanics is given in the source — flagged, not filled from external knowledge.
- **Observability tool identities not explicitly named on their comparison slide** (p.48): the slide describes three tooling categories by characteristics only (built-in with LangChain/LangGraph automatic trace; JSON logs + structured output; open standard for distributed tracing/dashboards) without printing product names in the visible text or slide layout (confirmed via page-image check, not just a text-extraction gap) — flagged as uncertain/unlabeled in the source itself; do not infer specific product names.
